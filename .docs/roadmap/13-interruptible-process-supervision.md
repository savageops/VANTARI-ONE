# 13 — Interruptible Process Supervision

**Priority: P0**

**Current delta (2026-08-12):** Move 7 closes Windows process-tree ownership,
bounded parent/child exit, and pipe-reader drain through one shared Job Object.
Move 16 closes byte-safe stdout/stderr persistence: raw pipe bytes become one
typed base64 event payload with stream and cap evidence, and installed replay
reconstructed exact stdout plus capped stderr. Operator cancellation during a
running command and richer post-kill classification remain open under this theme.

## The seam

`shell_exec` is the only tool that turns the model into an actor on the real machine: it spawns a process, drains its pipes, caps its output, watches a deadline, and on exit returns evidence the operator and the next turn must trust (AGENTS.md §V). A command run is the cost center with the widest blast radius — a misbehaving child can hang the turn, fill a pipe, escape the workspace, outlive its parent, or leave the session wedged with no reconcilable terminal state. AGENTS.md §X prices it explicitly: "process spawn, pipe draining, timeout, kill, output cap" and asks "Are stdout/stderr visible while the process runs and bounded at source?"

This theme owns the **supervision contract** for a single command run: (1) the process is killable as a *tree* on every platform, not just the direct child; (2) stdout/stderr stream as bounded, binary-safe deltas *while the process runs*, with a cap marker that does not deadlock the pipe; (3) an operator cancellation requested mid-run reaches the running process, not just the next step boundary; and (4) the terminal event carries post-kill evidence — exit code, killed-by class (timeout vs. cancel vs. signal), and the partial bytes captured before termination. It is the layer that themes 03 (typed event grammar) and 12 (binary-safe spine) project command I/O onto; this theme owns the *live process* those events describe.

## What exists today

- **Two platform-specific run paths share one pipe-draining core.** `runCommandWithLimitsPortable` (`apps/backend/src/core/tools/runtime.zig:419`) and `runCommandWithLimitsWindows` (`runtime.zig:562`) both spawn a `std.process.Child` with `stdout/stderr = .Pipe`, then hand each pipe to a `PipeCollector` running on its own `std.Thread` (`runtime.zig:464-465`, `:609-610`).
- **Pipe draining is already deadlock-safe.** `PipeCollector.readLoop` (`runtime.zig:538`) reads 4 KB frames; once `output.items.len >= max_output_bytes` it flips `cap_reached`, emits the cap marker through the callback exactly once, then `continue`s the loop — it **keeps reading and discarding** so the child's pipe never fills and blocks. The cap is enforced *at the collector*, not by closing the pipe. This is the correct primitive; both platforms inherit it.
- **Streaming deltas flow through one typed serializer.** `forwardCommandOutput` (`builtin/shell_exec.zig`) bridges raw `PipeCollector` slices into `ToolEventSink.onOutputDelta`; `serializeToolOutputDelta` base64-encodes them into `chunk_b64` with stream and `cap_reached` before ledger append. Output is visible while the process runs and byte-identical after cold replay.
- **Timeout exists, per platform, with different reach.** POSIX (`runtime.zig:467-489`) polls `waitpid(.., WNOHANG)` every 10 ms against a deadline and calls `child.kill()` on timeout. Windows (`runtime.zig:612-621`) calls `WaitForSingleObjectEx(child.id, timeout_ms, ..)` and on `error.WaitTimeOut` calls `windows.TerminateProcess(child.id, 1)` then waits infinite for the handle to signal. `CommandOutput.timed_out` is returned and rendered (`builtin/shell_exec.zig:218`, `module.zig:77`).
- **Output and timeout budgets are declared and clamped.** `shell_exec`'s schema clamps `timeout_ms` to `[1, 60000]` and `max_output_bytes` to `[1, 65536]` per stream (`builtin/shell_exec.zig:20-21`, `:56-57`). argv mode, workspace-contained cwd (`fsutil.resolveInWorkspace`), and shell/bash/powershell modes are all enforced (`:147-180`).

**Gap — four invariants are missing, and each is a real failure mode the code admits today:**

1. **No process-tree kill — only the direct child dies.** POSIX `child.kill()` (`runtime.zig:483`) sends SIGTERM to one PID; Windows `TerminateProcess(child.id, ..)` (`runtime.zig:617`) kills one handle. A `shell`/`bash`/`powershell` mode run is always `sh -lc`, `bash -lc`, or `powershell.exe -Command` — the model's command is a *grandchild*. On timeout the shell dies; the command it spawned is reparented and keeps running, holding locks, sockets, and build artifacts. AGENTS.md §XV ("child termination") and §V ("process termination") are **aspirational against the current code** for any command that forks.
2. **Cancellation is not propagated into a running command.** `Hooks.shouldCancel` is checked at the step boundary (`executor/loop.zig:178`, `:319`) and *after* a parallel batch joins (`executor/batch.zig:151`). The `CancellationToken` type is referenced in `batch.zig:102` but **is never defined** — grep finds zero definitions in `apps/backend/src`. A 60-second command cannot be interrupted by the operator; they can only wait for timeout or step completion.
3. **Windows pipe-close can hang past the child's exit.** When a Windows child spawns a daemonized descendant that inherits the stdout/stderr pipe handles, the child emits its exit but the pipe `read` does not return 0 because the grandchild still holds the handle open. The current code blocks on `child.wait()` after the join (`runtime.zig:629`) with no deadline on the close — a hung grandchild hangs the whole tool call. (This is the exact pathology pi-mono's `bash-close-hang-windows.test.ts` documents.)
4. **Post-kill evidence is partial.** `CommandOutput` carries `exit_code` and `timed_out` only (`module.zig:73-83`). There is no `killed_by` distinction (timeout vs. operator cancel vs. signal), no signal number on POSIX, no partial-byte count, and the Windows path returns `Error.CommandTerminated` for any non-`.Exited` term (`runtime.zig:632-635`) — dropping the exit code when the process was killed by a signal it could have reported.

## What the competitor does

### OpenAI Codex — `exec-server` + `command/exec` (the closest design)

Codex separates process supervision into its own JSON-RPC server (`codex-rs/exec-server/README.md`) and exposes it through the app-server as `command/exec` (`codex-rs/app-server/README.md:828-928`). The design is the reference shape for an interruptible command run:

- **Per-process lifecycle with a client-chosen id.** `process/start` takes a `processId`, `argv`, absolute `cwd`, `env`, and optional `tty`/`pipeStdin`. Output is streamed asynchronously as `process/output` notifications carrying `processId`, per-process `seq`, `stream` (`stdout`/`stderr`/`pty`), and **base64-encoded bytes** (`exec-server/README.md:213-226`). Exit arrives as a separate `process/exited` notification with `exitCode`; a final `process/closed` fires after the handle is removed.
- **Explicit terminate RPC.** `process/terminate` (`exec-server/README.md:183-209`) and `command/exec/terminate` (`app-server/README.md:911`) kill a running process by id. `turn/interrupt` (`app-server/README.md:716-728`) cancels an in-flight turn; the server "requests cancellation of the active turn, then emits a `turn/completed` event with `status: interrupted`." The terminate example returns `exitCode: 137` (SIGKILL) — post-kill exit evidence is preserved.
- **Connection-scoped lifetime — the strongest invariant.** "`command/exec/outputDelta` notifications are connection-scoped. If the originating connection closes, the server terminates the process" (`app-server/README.md:879`). A crashed or disconnected client cannot orphan a command; the supervisor reaps it. The exec-server README repeats this at the transport layer: "If the websocket connection closes, the server terminates any remaining managed processes for that client connection" (`exec-server/README.md:42-43`).
- **Per-stream cap with a final-chunk marker.** `outputBytesCap` "applies independently to `stdout` and `stderr`"; "`capReached` is `true` on the final streamed chunk for a stream when `outputBytesCap` truncates that stream; later output on that stream is dropped" (`app-server/README.md:877, 926`). Timeout and cap are independently disablable (`disableTimeout`, `disableOutputCap`) but mutually exclusive with their bounded counterparts — a clean contract.

**Limitations:** the README does not specify *how* termination kills the tree (the `codex-utils-pty` crate that owns it is not in the harvest), and Windows sandbox execution is explicitly second-class: "`command/exec/write` and `command/exec/terminate` are still unsupported for those requests" on buffered Windows sandbox runs (`app-server/README.md:872`). The connection-scoped reap is the invariant worth stealing; the Windows gap is the opening.

### Vercel Eve — durable `AbortController` + POSIX process-group escalation

Eve threads a single turn-scoped `AbortSignal` through the entire harness and binds it into the sandbox session:

- **Cancel signal is durable and Temporal-backed.** `turn-cancellation-control.ts` creates an `AbortController` whose signal is "serialized into every `turnStep`" and a session-scoped cancel *hook* (`createHook`) that survives crashes. The cancel request arrives through the hook iterator, `controller.abort(new TurnCancelledError())` fires, and `throwIfTurnAborted(abortSignal)` (`harness/turn-cancellation.ts`) throws at every step boundary. A crashed run replays the cancel deterministically because the hook reads are durable.
- **The signal is composed into every sandbox call.** `bindSandboxAbortSignal` (`execution/sandbox/abort-bound-session.ts`) returns a session wrapper that `AbortSignal.any([bound, call])`-composes the turn signal into every `run`/`spawn`/`readFile`. Tools receive `ctx.abortSignal` (`e2e/fixtures/agent-cancellation/agent/tools/wait-for-cancellation.ts`) and subscribe to `abort` to reject/cleanup cooperatively.
- **POSIX process-group escalation with bounded stages.** `local-server-process.ts` forks the dev server `detached` (its own process group) and closes with a three-stage budget: IPC graceful shutdown (550 ms) → `signalProcessGroup(child, "SIGTERM")` (150 ms) → `signalProcessGroup(child, "SIGKILL")` (100 ms), each racing `terminatesWithin` against `terminated.promise`. `signalProcessGroup` is `process.kill(-child.pid, signal)` — negative PID is the whole group.

**Limitation — and it is decisive for VANTARI's thesis:** Eve's process-group kill is **POSIX-only by construction**. `isProcessGroupAlive` returns `false` on `win32` (`local-server-process.ts:224`), and `signalProcessGroup` falls through to `child.kill(signal)` on Windows (`:233-241`) — direct-child only. Eve's own comment admits the POSIX mechanism's premise ("macOS has no parent-death signal"). The durable AbortController is excellent; the Windows kill is the same gap VANTARI's `TerminateProcess` has today.

### badlogic pi-mono — `taskkill /T` and the Windows pipe-close hang, documented

pi-mono's `coding-agent` package owns the most candid treatment of the two Windows failure modes:

- **Cross-platform `killProcessTree` (`utils/shell.ts:186`).** Windows: `spawn("taskkill", ["/F", "/T", "/PID", pid], { detached: true })` — `/T` walks the tree, `/F` force-terminates. POSIX: `process.kill(-pid, "SIGKILL")` with a single-PID fallback.
- **The Windows close-hang is named and tested.** `utils/child-process.ts:waitForChildProcess` documents the exact pathology: "On Windows, daemonized descendants can inherit the child's stdout/stderr pipe handles. In that case the child emits `exit`, but `close` can hang forever even though the original process is already gone." The fix is a post-`exit` grace timer (`EXIT_STDIO_GRACE_MS = 100`): after the child exits, wait briefly for stdio `end`; if it does not arrive, `child.stdout.destroy()` / `child.stderr.destroy()` and resolve anyway. `test/bash-close-hang-windows.test.ts` reproduces it (`spawn(.., { stdio:'inherit', detached:true })` + `child.unref()`) and asserts the run resolves within 3 s instead of hanging forever.
- **SIGTERM → SIGKILL escalation with a `killed` flag.** `core/exec.ts` kills with `SIGTERM`, schedules a 5 s `SIGKILL` follow-up, and returns `killed: boolean` distinct from `code`. `bash-executor.ts` separates `cancelled` (from `signal.aborted`) from `exitCode` (undefined when cancelled) and spills full output to a temp file when the in-memory rolling buffer overflows.

**Limitation:** `taskkill /T` shells out to an external process — a race window exists between spawn and kill where grandchildren can escape, and `taskkill` itself can fail silently (pi-mono swallows the error: "Ignore errors if taskkill fails"). It is an improvement over `TerminateProcess`, but it is not atomic and not guaranteed.

### Industry substrates

- **Windows Job Objects** are the OS-grade answer to process-tree termination. `CreateJobObject` + `AssignProcessToJobObject` capture *all* descendants automatically (children inherit the job), `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` kills the whole tree when the last job handle closes (parent-death reaping — the property macOS lacks and Eve works around with IPC), and `TerminateJobObject` synchronously kills every process in the job *and nested child jobs* in one call. ([learn.microsoft.com/windows/win32/procthread/job-objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject)). GitLab Runner switched to Job Objects for exactly this reason: "closing the job handle terminates all processes" on build cancel/timeout ([gitlab-runner MR 4525](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/4525)). The .NET runtime is migrating `Process.Kill(entireProcessTree)` onto `KILL_ON_JOB_CLOSE` for the same reason ([dotnet/runtime#126273](https://github.com/dotnet/runtime/issues/126273)).
- **POSIX process groups** are the Unix answer. Spawn the child in a new group (`setpgid`/`Command::process_group(0)`), then `killpg(pgid, SIGTERM)` → grace → `killpg(pgid, SIGKILL)` reaps the tree atomically. Reap with `wait4`/`waitid`. ([pubs.opengroup.org wait](https://pubs.opengroup.org/onlinepubs/009696899/functions/wait.html)). Tokio's `Child::kill()` + `kill_on_drop(true)` is the async glue; the `ClonableChild` pattern exists precisely because `tokio::process::Child`'s `kill` and `wait` both take `&mut self`, so you need a clone to kill while `wait` is in flight ([docs.rs/tokio/process/Child](https://docs.rs/tokio/latest/tokio/process/struct.Child.html)).
- **The pipe deadlock is a named law.** "Writing more than a pipe buffer's worth of input to stdin without simultaneously reading stdout and stderr causes a deadlock" — the OS pipe buffer is ~64 KB on Linux, and if nothing drains it the child's write blocks forever ([tey.sh subprocess pipe deadlocks](https://tey.sh/TIL/002_subprocess_pipe_deadlocks), [nodejs issue #3429](https://github.com/nodejs/node/issues/3429)). The only fix is concurrent draining — which VANTARI's two-`PipeCollector`-thread design already does.

## Why VANTARI does it better

1. **OS-grade tree kill on Windows where competitors shell out.** pi-mono spawns `taskkill.exe /T`; Eve falls through to direct `child.kill` on `win32`; Codex defers Windows terminate entirely. VANTARI will assign the child to a Job Object at spawn with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Timeout, cancel, and supervisor-drop all reduce to *one operation* — close the job handle (or `TerminateJobObject`) — and the kernel reaps the entire tree, including grandchildren that escaped `taskkill`'s snapshot. The supervisor process crashing is no longer an orphan risk: the kernel kills the job when the last handle goes. This is the only mechanism that makes "process termination" (AGENTS.md §V) a true invariant on Windows rather than a best-effort shell-out.
2. **Process-group kill on POSIX, with the same escalation budget Eve proved.** The portable path will spawn the child in its own process group and kill with `killpg(SIGTERM)` → bounded grace → `killpg(SIGKILL)`, mirroring Eve's IPC→SIGTERM→SIGKILL stages. Atomic group kill beats pi-mono's `/proc`-walk (grandchildren escape between enumerate and signal) and matches Eve's reach — without inheriting Eve's Windows blind spot.
3. **Cancellation reaches the running process, not just the next step.** Today `shouldCancel` is polled at step boundaries and `CancellationToken` is an undefined symbol (`batch.zig:102`). VANTARI will define a real token (an atomically-flagged struct threaded through `CommandLimits`, the same seam `output_callback` already uses) and poll it inside the POSIX `waitpid` loop and the Windows wait — so an operator cancel kills the job *during* the run, seconds after the request, with a terminal `tool_finished` carrying `killed_by: cancel`. Eve's durable AbortController is the model for the *signal*; VANTARI's owned kernel loop is what makes the *kill* immediate instead of cooperative-only.
4. **The pipe-draining primitive is already correct — no redesign.** VANTARI's `PipeCollector` already keeps reading after the cap (`runtime.zig:544-548`) to prevent the pipe-buffer deadlock, and already streams `chunk_b64` deltas with a one-shot `cap_reached` marker through the typed event spine. Codex and pi-mono had to discover this independently; VANTARI shipped it. The supervision work reuses this core unchanged and focuses entirely on *kill reach* and *evidence*.
5. **Windows close-hang solved at the wait, not by luck.** VANTARI will adopt pi-mono's documented grace-then-destroy pattern as a bounded post-exit wait on the pipe threads: after the child handle signals exit, join the drain threads with a small budget; if they do not join (grandchild holds the inherited handle), destroy the handles and proceed. The run resolves on the child's exit, not on a daemonized grandchild's pleasure.
6. **Post-kill evidence is typed, not boolean.** `CommandOutput` gains a `killed_by` enum (`timeout | cancel | signal | exited`) and the Windows path stops collapsing every non-`.Exited` term to `Error.CommandTerminated`. The terminal `tool_finished` event (theme 03) carries the class, the partial stdout/stderr bytes captured before termination, and on POSIX the signal number. "Works" is not a mechanism; `killed_by: timeout, captured_bytes: 4096, signal: null` is.

### TARGET SUPERVISION ROW (per command run)

```text
spawn:
  POSIX  -> setpgid(0) so the child is a group leader
  Win32  -> CreateJobObject(KILL_ON_JOB_CLOSE) + AssignProcessToJobObject(child)
drain:   two PipeCollector threads (existing) -> tool_output_delta events (existing)
deadline + cancel:
  poll waitpid(WNOHANG) / WaitForSingleObjectEx against {deadline, cancel_token}
  on fire: kill the tree (killpg or TerminateJobObject), bounded grace, then SIGKILL/force
terminal evidence:
  { exit_code, killed_by: timeout|cancel|signal|exited, captured_bytes, signal? }
```

## Pipeline items under this theme

### P0-13a: Process-tree termination — Job Objects (Windows) and process groups (POSIX)
- **Contract:** every `shell_exec` run kills the *entire* descendant tree on timeout, cancel, or supervisor drop — not just the direct child. On Windows the child is assigned to a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` at spawn; termination is `TerminateJobObject` (or close-the-handle on drop). On POSIX the child is spawned in its own process group; termination is `killpg(SIGTERM)` → bounded grace → `killpg(SIGKILL)`. AGENTS.md §V ("process termination") and §XV ("child termination") become true invariants.
- **Mechanism:** extend `runCommandWithLimitsWindows` (`runtime.zig:562`) to create the job, assign the child before it can fork (per MSDN, assignment must race the child's first instruction — use `CREATE_SUSPENDED` then `AssignProcessToJobObject` then `ResumeThread`), and replace `TerminateProcess(child.id, ..)` (`:617`) with `TerminateJobObject`. Extend `runCommandWithLimitsPortable` (`runtime.zig:419`) to set a process group via `std.posix.setpgid` and replace `child.kill()` (`:483`) with a `killpg` escalation. No new tool, no new event type — the kill reach changes, the seam does not.
- **Test (AGENTS.md §XIV "command timeout and process locks"):** a `shell_exec` running `powershell -Command "Start-Process node -ArgumentList '-e','sleep 60' ; sleep 60"` (Windows) and `sh -lc 'sleep 60 & sleep 60'` (POSIX), killed by timeout, leaves zero surviving descendants after a bounded reap window — verified by enumerating the job (Win) / process group (POSIX) after termination.
- **Proof:** native installed `%LOCALAPPDATA%\Vantari\bin\vantari.exe` run on Windows; `tasklist` after the killed run shows no orphaned sleep. Session/event evidence records the tree kill in `tool_finished`.

### P0-13b: Bounded pipe draining with cap markers (close the Windows close-hang)
- **Contract:** stdout/stderr stream as byte-safe bounded deltas with a per-stream cap and a one-shot `cap_reached` marker *while the process runs* (AGENTS.md §IV), and a run whose child exits never blocks forever on a pipe held open by an inherited descendant handle (the pi-mono `bash-close-hang-windows` pathology).
- **Mechanism:** the existing `PipeCollector` read-loop (`runtime.zig:538`) already drains-after-cap — keep it unchanged. Add a bounded post-exit join on the drain threads in both run paths: after the child handle signals exit, `stdout_thread.join()` / `stderr_thread.join()` with a small budget; on timeout, `file.close()` the inherited handles to break the blocked read and proceed. This is the kernel-native equivalent of pi-mono's `EXIT_STDIO_GRACE_MS = 100` + `stdout.destroy()`.
- **Test (AGENTS.md §XIV):** a Windows run whose child spawns a `detached`/`inherit-stdio` grandchild that outlives the shell resolves within a bounded budget (e.g. 3 s) after the shell exits, returns the partial output, and does not hang the tool call — the exact scenario in `.refs/badlogic__pi-mono/packages/coding-agent/test/bash-close-hang-windows.test.ts`.
- **Proof:** the §XIV adversarial list ("command timeout and process locks", "stdout/stderr cap markers") passes; a `tool_output_delta` with `cap_reached: true` precedes `tool_finished`.

### P1-13c: Cancellation token propagation — operator → executor → process
- **Contract:** an operator cancellation requested while a `shell_exec` is *running* reaches the live process within a bounded latency and terminates it, instead of waiting for timeout or step completion. The token is defined (today `CancellationToken` is referenced in `batch.zig:102` but undefined), threaded through `CommandLimits`, and polled in the run loop alongside the deadline.
- **Mechanism:** define `pub const CancellationToken = struct { flag: std.atomic.Value(bool), .. }` in `core/tools/module.zig` (the seam `output_callback` already lives in); add `cancel_token: ?*const CancellationToken` to `CommandLimits` (`module.zig:112`); poll it in the POSIX `waitpid` loop (`runtime.zig:471`) and the Windows wait (`:614`) — whichever fires first (deadline, cancel, or exit) wins. The executor passes a session-scoped token derived from `Hooks.shouldCancel` so the existing cancel hook drives the live kill.
- **Test:** a `shell_exec` with `timeout_ms: 60000` running `sleep 30`, cancelled by the operator 1 s after `tool_started`, terminates within a bounded latency (e.g. 2 s) and emits `tool_finished` with `killed_by: cancel`; without the cancel it would run the full 30 s.
- **Proof:** session/event evidence shows `tool_started` → (cancel requested) → `tool_finished(killed_by=cancel)` with wall-clock duration << timeout_ms.

### P1-13d: Post-kill evidence — exit code, killed-by class, partial bytes
- **Contract:** the terminal `CommandOutput` and `tool_finished` event distinguish *why* the process ended — `exited | timeout | cancel | signal` — carry the exit code when available, the POSIX signal number when signaled, and the count of stdout/stderr bytes captured before termination. The Windows path stops returning `Error.CommandTerminated` for signal kills and instead surfaces the class as data.
- **Mechanism:** extend `CommandOutput` (`module.zig:73`) with `killed_by: KilledBy` (enum) and `captured_stdout_bytes`/`captured_stderr_bytes: usize`; thread through `renderResult` (`builtin/shell_exec.zig:196`) into the JSON envelope and the `ToolFinished` event struct (`shared/protocol/events.zig:16`). On Windows, a term that is `.Signal` after `TerminateJobObject` maps to `killed_by: timeout|cancel` rather than `Error.CommandTerminated`.
- **Test (AGENTS.md §XIV):** a timed-out run returns `{"timed_out":true,"killed_by":"timeout","exit_code":1,"captured_stdout_bytes":N}`; a cancelled run returns `killed_by:"cancel"` with `exit_code` null/1 and a non-zero `captured_stdout_bytes` when output preceded the kill.
- **Proof:** the §XIV adversarial list ("command timeout and process locks") asserts the `killed_by` class and partial-byte count, not just a boolean.

### P2-13e: Detached-process accounting and supervisor-drop reconciliation
- **Contract:** if a process escapes the job/group (a `detached`/`unref`'d grandchild on Windows that dodged `AssignProcessToJobObject`, or a POSIX `setsid` child), the supervisor records the orphan and reconciles it at the next run start — the cold-start equivalent of Codex's "connection closes → terminate" and pi-mono's `trackedDetachedChildPids`.
- **Mechanism:** a `.var/sessions/<id>/orphans.jsonl` ledger of PIDs that escaped tree-kill, reconciled by the session-open path (best-effort reap; the Job Object's `KILL_ON_JOB_CLOSE` makes this rare on Windows, but a `CREATE_BREAKAWAY_FROM_JOB` child can still escape).
- **Test:** a command that force-breaks from the job leaves an orphan row; the next session open reaps it or records a durable reconciliation event.

## North-star link

A shard that branches into its own context window (theme 01) and delegates to children (theme 06) is only trustworthy if every command those branches run is *interruptible* and *reconcilable*. A long-running build in a child shard that cannot be cancelled mid-flight blocks the parent's `wait_agent`; a timed-out shell that orphans a server process holds the port across cold start and corrupts the next run's evidence. Interruptible process supervision is what makes a tool span a bounded, killable, evidenced unit of work — the same property that makes a shard a bounded, replayable unit of context. Without tree-kill reach, live cancellation, and post-kill evidence, "the operator can observe the same causal chain the kernel will replay after cold start" (AGENTS.md §I) is false the first time a model runs `npm run dev` and the operator hits cancel.

## Definition of done
- Every `shell_exec` run kills the full descendant tree on timeout, cancel, and supervisor drop: Job Objects on Windows, process groups on POSIX (AGENTS.md §V, §XV).
- Operator cancellation requested during a running command terminates it within bounded latency, evidenced by a `tool_finished(killed_by=cancel)` event — not deferred to the next step boundary.
- stdout/stderr stream as byte-safe bounded deltas with a per-stream cap marker while the process runs; a run whose child exits never hangs on an inherited Windows pipe handle (AGENTS.md §IV, §XIV).
- Terminal evidence carries `killed_by` class (exited/timeout/cancel/signal), exit code, and partial captured bytes on every code path; the Windows path no longer collapses signal kills to `Error.CommandTerminated`.
- The §XIV adversarial list (command timeout, process locks, stdout/stderr cap markers) passes and gates promotion, with a native installed `vantari.exe` proof on Windows.
- No second command-run path, no shell-out to `taskkill` as the primary kill mechanism (Job Objects own it), no parallel cancellation surface — the existing `PipeCollector` core and `tool_output_delta` event grammar are reused unchanged.
