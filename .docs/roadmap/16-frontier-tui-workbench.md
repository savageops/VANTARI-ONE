# 16 — Frontier TUI Workbench

**Priority: P1**

## The seam

The TUI is the only operator surface that runs in the same process lane as the kernel and renders the causal chain as it happens. AGENTS.md §I forbids it from assembling provider context, inferring tool state, or keeping its own transcript truth — "CLI/TUI/browser clients never assemble provider context, infer tool state, or maintain their own transcript truth. They render kernel-owned state." AGENTS.md §IV tightens that into a read-model contract: "TUI progress is a read model over `events.jsonl`, not a separate speculative status bus," "Tool spans update a single keyed row in clients. Do not append request/start/done rows for one tool invocation," and the cost-center question for a TUI frame is "Does the interface preserve transcript comprehension under live updates?" (§X).

This theme owns the **workbench contract**: (1) the render loop is a pure projection of the typed event spine (theme 03/12) at a monotonic cursor, with no speculative status the kernel did not emit; (2) a tool invocation is one keyed row whose text mutates through its lifecycle (`running` → `42ms` / `error …`), never a request row plus a start row plus a done row; (3) the assistant token stream appends into one growing buffer with the operator's scroll anchor preserved while live output continues below; (4) command stdout/stderr are untrusted, ANSI-stripped, cap-marked display text, not parsed content; and (5) cancellation reaches the running turn within bounded latency through the existing `session_cancel` RPC, not a second control bus. It is the layer that themes 03 (event grammar), 12 (binary-safe spine), and 13 (interruptible supervision) project onto the operator's eye; this theme owns the *frame* those events become.

## What exists today

- **A libvaxis-backed single-pane chat surface.** `apps/backend/src/clients/tui_chat.zig` (`mainWithMode`, `:754`) enters the alt screen, enables mouse and Kitty keyboard, and renders one `ChatState` through `draw` (`:915`): a transcript window above a lifted composer with a one-row metadata footer (workspace / model / provider / transient status). The `tui` import is the vendored `vantari_tui` package (`packages/tui`, rebranded libvaxis; `apps/backend/build.zig.zon:35`), so the screen is double-buffered and diff-rendered by the library — VANTARI does not hand-roll the cell grid.
- **The read-model contract is already implemented and is the strongest part.** `ChatState.recordProgressEvent` (`:346`) consumes typed events; `addProgress` (`:378`) drops `tool_requested`/`tool_completed` noise and routes `tool_started` → `upsertToolStarted` (`:401`), `tool_finished` → `upsertToolFinished` (`:421`), and `tool_output_delta` → `upsertToolOutputDelta` (`:479`). `addToolProgress` (`:454`) and `appendToolProgress` (`:505`) upsert by `tool_call_id` — a tool invocation occupies exactly one row whose text is rewritten across its lifecycle. The tests `tui tool lifecycle updates one progress row instead of appending request start done rows` and `tui chat state coalesces assistant tokens and streams repeated command output into one row` (`:2141`, `:2105`) prove the §IV "single keyed row" invariant holds.
- **Assistant deltas stream into one buffer with scroll preservation.** `addAssistantDelta` (`:528`) `realloc`s the last assistant message in place, and when the operator is scrolled up it advances `scroll_offset` by the delta in *wrapped row count* (`:542-545`) so the anchored row stays on screen. `tui streamed assistant deltas preserve row scroll anchor as wrapping grows` (`:2572`) and `tui keeps the operator's scroll anchor while live output continues below` (`:2312`) assert the §X "preserve transcript comprehension under live updates" property against growing content.
- **Two-source cursor with durable fallback.** `drainProgress` (`:294`) pulls live notifications via `waitForNotificationAfter(last_notification_sequence, …)` over the stdio bus, where `Notification.sequence` is a monotonic `u64` (`host/stdio_rpc.zig:209`, `next_notification_sequence` `:227`). `syncDurableProgressIfDue` (`:315`) re-reads `session_get` every 350 ms (`durable_sync_interval_ms`) and reconciles from `last_durable_event_count` — a torn notification stream cannot lose events because the durable ledger is the backstop. `markProgressEventSeen` (`:359`) dedups by `timestamp\x1f type\x1f message`, so same-millisecond bursts (AGENTS.md §IV "Event cursors use monotonic ledger position … Timestamp-only cursors are insufficient") survive replay.
- **Untrusted command output is already sanitized.** `formatToolOutputDelta` (`:1533`) base64-decodes `chunk_b64`, runs it through `normalizeTerminalChunk` (`:1763`) which strips CSI/SGR escapes, honors `\r` overwrite and `\x08` backspace, replaces non-printables, then `compactOutputPreview` (`:1703`) flattens to one bounded line with a `(N lines)` marker and a `[cap]` suffix. `appendBoundedProgress` (`:1678`) keeps a tail-bounded single row (`max_tool_output_payload_bytes = 180`). The tests `tui progress renders hostile output chunks without corrupting the transcript surface` and `tui progress strips terminal color controls from streamed command output` (`:1865`, `:2057`) prove the §IV "render output as bounded display text" invariant.
- **Cancellation is wired but step-bounded.** `requestCancel` (`:685`) calls `session_cancel` once, flips `status = "CANCELLING"`, and shows a footer affordance. Cancellation reaches the kernel; whether it reaches a *running* process mid-flight is theme 13's job (`CancellationToken` is still an undefined symbol — `core/tools/executor/batch.zig:102`).

**Gap — five invariants are missing, and the workbench is not yet the frontier surface the north star needs:**

1. **No live item graph.** The transcript is a flat vertical list. A branch shard (theme 01) and a delegated child (theme 06) render as ordinary progress rows; their *convergence* is invisible. The operator cannot see "shard A/B/C branched at seq 40 and merged back" — the defining structure of the north-star architecture is collapsed into append-only text. The `.docs/log.txt` TUI history (lines 336–349) repeatedly asks for live, real-time visibility of backend work; today branching is not a first-class render object.
2. **The render loop is poll-driven, not event-driven.** `executePromptTurn` (`:213`) spins on `progress_poll_ms = 60` ms (`:271`) inside `while (!send_job.isDone())`, draining notifications then sleeping. Frame rate is decoupled from event arrival: a 60 ms idle poll burns CPU, and a fast delta burst coalesces into one frame only because `draw` is called once per loop iteration. There is no frame budget, no dirty-region tracking above the library's cell diff, and the render thread is the input thread — typing and streaming share one `loop.nextEvent()`/draw cycle.
3. **Scrollback is in-memory and unbounded.** `ChatState.messages` is an `ArrayList(Message)` that grows for the whole session; there is no eviction. `loadSession` (`:102`) hydrates *every* message and *every* event into `messages` on cold start. A long session with heavy tool output holds the full transcript in TUI memory and re-wraps it on every resize (`appendWrappedTranscriptRows` rebuilds all rows each `draw`).
4. **No raw-event inspection surface.** When a tool row says `error InvalidArguments`, the operator cannot see the underlying `tool_finished` JSON envelope without leaving the TUI. Debugging the event spine (theme 12) requires a side channel (`var run --json`, reading `events.jsonl`). AGENTS.md §XVIII item 10 lists "optional raw event inspection" as a workbench deliverable.
5. **Cancellation evidence is not rendered as a terminal span.** `requestCancel` shows `cancelling`, but the terminal `tool_finished(killed_by=cancel)` evidence theme 13 will emit has no dedicated render — it lands as a generic progress row, indistinguishable from a normal completion.

## What the competitor does

### badlogic pi-mono — `@mariozechner/pi-tui` differential renderer + `chatContainer` append model

pi-mono ships its own TUI framework (`packages/tui/src/tui.ts`, 1243 lines) with a hand-written **differential renderer** and a chat surface in `packages/coding-agent/src/modes/interactive/interactive-mode.ts`:

- **Line-level diff with synchronized-output batching.** `render()` produces `string[]` (one entry per terminal row); the renderer compares `newLines` against `previousLines`, finds `firstChanged`/`lastChanged`, and writes only the changed span, moving the hardware cursor with `\x1b[<n>A/B` and clearing with `\x1b[2K`. The whole batch is wrapped in `\x1b[?2026h` … `\x1b[?2026l` (DECSET 2026 synchronized output) so the terminal flushes one frame atomically (`tui.ts:905-1049`). Width change, height change, and shrink-below-max each trigger a bounded `fullRender(true)` that clears with `\x1b[2J\x1b[H\x1b[3J`.
- **Append-per-message, not keyed-row upsert.** `addMessageToChat` (`interactive-mode.ts:2998`) switches on `message.role` and `chatContainer.addChild(component)` for each `user` / `assistant` / `bashExecution` / `compactionSummary` / `branchSummary` message. A bash execution is its own `BashExecutionComponent` appended to the container; tool results render *inline within the assistant message's tool-call list*. There is no `tool_call_id`-keyed row that mutates through `running` → `done` — each lifecycle fact is a new child or an in-place mutation of the component's own state, recomposited on the next `render()`.
- **OSC 133 prompt zones for shell integration.** `AssistantMessageComponent.render` (`components/assistant-message.ts:61`) wraps its first/last line in `\x1b]133;A\x07` / `\x1b]133;C\x07` so the terminal emulator can fold the assistant turn as a semantic block.
- **Bounded widget overflow, not transcript eviction.** `MAX_WIDGET_LINES = 10` (`interactive-mode.ts:1805`) caps *extension widget* content; the chat history itself relies on the terminal's own scrollback plus the differential re-render keeping the visible viewport correct. There is no explicit "operator scrolled up, hold the anchor while streaming" invariant tested the way VANTARI's `tui keeps the operator's scroll anchor while live output continues below` tests it.

**Limitation — and it is decisive for the §IV contract:** pi-mono's TUI *is* the transcript truth in the render path. `chatContainer.children` is the live message list; hydration rebuilds it from `SessionContext.messages`. If the model emits a tool call and then a tool result, the renderer depends on the session layer handing it two distinct messages to add as children — it does not enforce "one tool invocation = one keyed row" as a structural invariant. VANTARI's `tool_call_id` upsert is the contract pi-mono approximates with component mutation but does not guarantee.

### OpenAI Codex — `codex-rs/tui` (ratatui) + `app-server` item stream

Codex separates the TUI from the protocol: a Rust `tui` crate (ratatui/crossterm, referenced in `codex-rs/README.md` and `codex-rs/tui/src/onboarding/`) consumes an `app-server-client` that speaks the `app-server` JSON-RPC item stream:

- **ratatui double-buffer diff.** ratatui "calculates a diff between the current buffer and the previous buffer to figure out what content to write to the terminal" (`ratatui.rs/concepts/rendering/under-the-hood`). The TUI draws widgets into a back buffer, the library diffs against the front buffer, and only changed cells are emitted — the same primitive libvaxis gives VANTARI.
- **Items are the unit of render, typed by the protocol.** `app-server` streams `item`-shaped events (token output, tool call, reasoning, file changes). The TUI holds a list of items and re-renders the changed ones. `turn/interrupt` (`app-server/README.md:716`) cancels an in-flight turn and the server "emits a `turn/completed` event with `status: interrupted`" — the terminal fact is a typed event, not a TUI-local guess.
- **Connection-scoped lifetime.** "If the originating connection closes, the server terminates the process" (`app-server/README.md:879`) — the TUI is one client of a supervised server, never the owner of run state.

**Limitation:** the full chat-render source (`codex-rs/tui/src` chat loop, the ratatui `List`/`Paragraph` widget composition) is not in this harvest — only `onboarding/` and `login.rs` survived. The protocol shape (typed items, interrupt → terminal event) is the steal; the widget composition is inferred.

### Claude Code — Ink (React) reconciliation + synchronized-output proxies

Claude Code's terminal surface is a React app over Ink (`github.com/vadimdemedes/ink`; confirmed by multiple internals write-ups). React reconciliation against a previous frame is the diff engine; a streaming token span re-renders only itself, and the spinner span is rewritten in place once tokens begin, then collapses into a summary when the block completes. Community evidence (`claude-code` issue #29213 "Terminal output is not streaming", the `CLAUDE_CODE_NO_FLICKER` flag, the "Claude Chill" PTY proxy that "reduces flicker by 85%") shows the production surface is flicker-prone over SSH/tmux *without* synchronized output and clean with it — the exact DECSET 2026 bracketing pi-mono ships and VANTARI's libvaxis inherits.

### Vercel Eve — no TUI at all

Eve (`packages/eve/`) is web-only. Its operator surface is a browser over a Temporal-durable harness. There is no terminal client. This is the opening VANTARI's single-binary `vantari -c` TUI exploits: Eve's operator must run a web server and a browser to observe a workflow; VANTARI's operator runs one native binary that is its own kernel *and* its own operator surface on Windows, the platform Eve does not serve.

### Industry substrates

- **Double buffer + cell diff** is the law every performant TUI converges on. ratatui, libvaxis (VANTARI's substrate), and Textual all keep a previous screen buffer and emit only changed cells — full-frame redraws flicker and saturate the PTY (`ratatui.rs/concepts/rendering/under-the-hood`, `ratatui.rs/faq`). pi-mono rediscovers this at the *line* level (`tui.ts:984-998`); the cell level is strictly tighter.
- **DECSET 2026 synchronized output** (`\x1b[?2026h` … `\x1b[?2026l`) brackets a frame so the terminal holds the partial batch and flushes atomically. It is "tear-free rendering" for terminals (`vtdn.dev/docs/decset/mode2026-sync-output`, the Christian Parpart spec gist), the fix the Claude Code community reached for, and already what pi-mono emits and libvaxis emits for VANTARI.
- **Scroll-anchor preservation under live append** is the known hard problem. The `oh-my-pi#1295` issue ("Terminal scroll position jumps during active TUI redraws") names the pathology: the user scrolls up, a redraw jumps the viewport back. ratatui's `inline` viewport exists to "preserve the cursor's relative position" (`docs.rs/ratatui/struct.Terminal.html`); the robust answer is an explicit `scroll_offset` measured in *content rows*, advanced by the row-delta of any mutation below the anchor — which is exactly the mechanism VANTARI's `addAssistantDelta`/`addToolProgress` already implement and test.
- **OSC 133 prompt zones** (`\x1b]133;A..C`) let terminal emulators fold semantic blocks (user/assistant turns) for scrollback navigation. iTerm2, WezTerm, Ghostty, and Kitty implement it; pi-mono emits it; it is the cheapest win for "transcript comprehension" over a long session.

## Why VANTARI does it better

1. **The read-model contract is structural, not cosmetic.** pi-mono appends a component per message and relies on component mutation to approximate "one tool = one row"; Claude Code's React reconciliation has no concept of a `tool_call_id`-keyed row at all. VANTARI's `addToolProgress`/`appendToolProgress` upsert *by `tool_call_id`* (`tui_chat.zig:454`, `:505`) and the test `tui tool lifecycle updates one progress row instead of appending request start done rows` (`:2141`) asserts that `tool_requested` + `tool_started` + `tool_finished` + `tool_completed` produce exactly **one** row whose text moves `running` → `42ms`. This is AGENTS.md §IV's "Do not append request/start/done rows for one tool invocation" enforced as a tested invariant, not a styling choice. No competitor makes that guarantee with a falsification test.
2. **The cursor is monotonic and dual-sourced; the frame is a pure projection.** The TUI renders from `Notification.sequence` (monotonic `u64`, `stdio_rpc.zig:209`) with a 350 ms durable-ledger backstop (`syncDurableProgress`). A crashed notification stream cannot corrupt the view because `events.jsonl` is the reconciliation source — the same property theme 12 proves for the spine. pi-mono's TUI trusts its in-memory `chatContainer` and a single session-context hydration; Codex trusts its app-server stream but the connection-scoped reap is server-side, not a TUI-local cursor. VANTARI's TUI never owns truth it cannot re-derive from the ledger after cold start.
3. **Scroll-anchor preservation is tested under live growth.** `tui keeps the operator's scroll anchor while live output continues below` (`:2312`) and `tui streamed assistant deltas preserve row scroll anchor as wrapping grows` (`:2572`) prove the operator's viewport stays put while the assistant streams and tool output appends below — measured in wrapped-row deltas, not pixels. This is the `oh-my-pi#1295` pathology, solved and falsification-tested. pi-mono has no equivalent test; ratatui's `inline` viewport approximates it at the library level without a per-content-row invariant.
4. **Untrusted output is sanitized at the render boundary, by contract.** `normalizeTerminalChunk` strips ANSI/CSI, honors `\r`/`\x08`, drops non-printables, and `appendBoundedProgress` keeps a 180-byte tail bound per output stream. The tests `tui progress renders hostile output chunks without corrupting the transcript surface` and `tui progress strips terminal color controls` (`:1865`, `:2057`) prove a malicious `printf '\e[31mred\e[0m'` or a carriage-return spinner cannot wreck the transcript. AGENTS.md §IV "Command stdout/stderr are untrusted data … render output as bounded display text" is a tested render invariant. Competitors sanitize too, but none gate it with an adversarial test list (AGENTS.md §XIV "terminal scrollback under live streaming").
5. **The substrate is already double-buffered and sync-output capable.** libvaxis (`packages/tui`) gives VANTARI the cell-diff back buffer and DECSET 2026 frame batching that ratatui gives Codex and that pi-mono reimplemented by hand. VANTARI did not pay the line-diff rediscovery cost pi-mono paid (`tui.ts:984-1049`); it composes on a cell-diff library and spends its own code on the *content* invariants (keyed rows, anchor preservation, output sanitization) the library does not provide.

## Pipeline items under this theme

### P1-16a: Event-driven render loop with monotonic cursor and frame budget
- **Contract:** the TUI render loop is driven by event availability on the notification bus plus a bounded idle-poll backstop, not a fixed 60 ms sleep. Frames are produced on a dirty flag set by `recordProgressEvent`/`addAssistantDelta`/input, capped at a frame budget (e.g. 60 fps / ~16 ms), and the durable `session_get` reconciliation remains the cold-start-safe backstop. AGENTS.md §IV ("read model over `events.jsonl`") and §X ("TUI frame: event replay, wrapping, terminal render, scroll state") are honored with the cursor as the only render trigger.
- **Mechanism:** in `executePromptTurn` (`tui_chat.zig:213`), replace the fixed `progress_poll_ms` sleep with `drainProgress(session_id, frame_budget_ms)` returning a `changed` count; call `draw` only when `changed > 0` or an input event arrived, and clamp the loop to a maximum frame rate. The monotonic cursor (`last_notification_sequence` + `last_durable_event_count`) is already correct — this item removes the poll, not the cursor. Keep `waitForNotificationAfter` as the blocking-with-timeout primitive so an idle turn burns no CPU.
- **Test (AGENTS.md §XIV "terminal scrollback under live streaming", "same-millisecond event bursts"):** a simulated burst of N `assistant_delta` events in one drain produces at most one `draw` call; an idle turn with no events for 1 s produces zero `draw` calls; the cursor still advances past every event after the burst.
- **Proof:** a frame-count probe (behind a debug flag) shows `draws ≤ events` under burst and `draws == 0` under idle, with no event dropped from the projection.

### P1-16b: Tool span single-row lifecycle model (typed, terminal-evidenced)
- **Contract:** one tool invocation occupies exactly one keyed row for its entire lifecycle (`tool_requested` suppressed → `tool_started` inserts → `tool_output_delta`* appends in place → `tool_finished` rewrites → `tool_completed` suppressed), keyed by `tool_call_id`. When theme 13 ships `killed_by`, the row's terminal state is `{ok 42ms | error Name (hint) 4ms | cancelled | timeout}` — a typed terminal fact, not a string. AGENTS.md §IV ("Tool spans update a single keyed row") is the invariant; this item hardens it against the new terminal evidence.
- **Mechanism:** the upsert path (`addToolProgress` `:454`, `upsertToolFinished` `:421`) already exists. Extend `ToolFinished` rendering to branch on a `killed_by` field (theme 13d's `CommandOutput.killed_by`) and render `cancelled`/`timeout` distinctly from `error`. Add a coalescing test that fires `tool_started` + 5× `tool_output_delta` + `tool_finished(killed_by=cancel)` and asserts one row whose final text is `shell_exec cancelled`.
- **Test (AGENTS.md §XIV):** the existing `tui tool lifecycle updates one progress row …` (`:2141`) is extended to cover `killed_by`; a cancel-during-run produces a row that reads `cancelled`, not a second row.
- **Proof:** session/event evidence of a cancelled run projects to exactly one row in the TUI with terminal text matching the `tool_finished.killed_by` class.

### P1-16c: Live assistant delta streaming with bounded scrollback and anchor preservation
- **Contract:** the assistant token stream appends into one growing buffer, the operator's scroll anchor stays fixed while output continues below it, and the in-memory transcript is bounded (eviction of old rows beyond a cap) so a long session does not hold the full transcript in TUI memory or re-wrap it on every resize. Cold-start hydration (`loadSession`) projects from `messages.jsonl` + `events.jsonl`, not from an unbounded in-memory list.
- **Mechanism:** keep `addAssistantDelta`'s realloc-and-adjust-`scroll_offset` (`:528`) unchanged — it is correct. Add an eviction policy to `ChatState.messages`: once `messages` exceeds a row-budget (computed from `transcriptRowCount`), drop the oldest non-pending messages and rely on the ledger (the transcript is append-only and never lost — theme 02). On resize, cache wrapped-row counts per message keyed by `(text.ptr, body_width)` instead of recomputing the whole list each `draw`.
- **Test (AGENTS.md §XIV "terminal scrollback under live streaming"):** extend `tui keeps the operator's scroll anchor while live output continues below` (`:2312`) to a 500-message session: after eviction the anchor still holds, `transcriptRowCount` reflects only the resident window, and cold-start re-hydration reproduces the same visible state.
- **Proof:** a session with >cap messages renders at constant memory and constant re-wrap cost on resize, with no row the operator scrolled to being lost while live output appends.

### P2-16d: Item-graph visualization for branch/converge (shard projection)
- **Contract:** when theme 01 (sharded context) and theme 06 (delegation) emit branch/converge events, the TUI renders them as a graph object — a shard node with a parent edge, a status (`open | converged | abandoned`), and a converge edge back to the parent — not as flat progress rows. The graph is a read model over `context.jsonl` shard checkpoints and `events.jsonl` child-run edges; the TUI never invents topology.
- **Mechanism:** add a `GraphPanel` (collapsible, toggled by a keybind) that reads the session's shard checkpoints (theme 01's `shard_checkpoint` entries) and child-run tool events (`launch_agent`/`agent_status`/`wait_agent`), and renders an ASCII tree (`parent ─┬─ shard A [open] ├─ shard B [converged] └─ shard C [abandoned] → merged`). This is a new *projection*, not a new source of truth — it reads what the kernel already persisted.
- **Test:** a session with one parent and three branches (two converged, one abandoned) renders the tree with correct statuses after cold start; convergence is shown as an edge, not a new node.
- **Proof:** the panel's content is byte-identical to a projection of `context.jsonl` + `events.jsonl`, proving it is a pure read model.

### P2-16e: Raw event inspector panel (debugging surface)
- **Contract:** a toggle panel renders the raw typed events from `events.jsonl` at the current cursor — schema, `tool_call_id`, stream, `cap_reached`, `killed_by`, timestamps — so an operator debugging a tool failure or a replay discrepancy can inspect the envelope without leaving the TUI or running `var run --json`. AGENTS.md §XVIII item 10 ("optional raw event inspection") is the deliverable.
- **Mechanism:** add an `EventInspectorPanel` that, when toggled, renders the last N entries of the resident event projection (the same list `syncDurableProgress` already walks) as pretty-printed JSON, bounded and ANSI-safe. It shares the cursor with the transcript; selecting a tool row jumps the inspector to that event.
- **Test:** the panel renders a `tool_finished` envelope with `error_name` and `hint` fields intact and bounded; a hostile `chunk_b64` payload does not corrupt the panel layout.
- **Proof:** the panel's content for a given event matches `events.jsonl` byte-for-byte for the schema-owned fields, proving it is inspection, not interpretation.

## North-star link

The north star (theme 01) is "every message is a new context window, each step branches into its own shard, all branches converge and are reprocessed." That architecture is invisible to the operator in a flat transcript. A workbench that renders the item graph makes branching and convergence *the primary thing the operator sees* — the shard tree *is* the session's shape, and its convergence edges are the proof that branches were reprocessed, not abandoned. The read-model contract (§IV) is what makes that graph trustworthy: it is a projection of `events.jsonl` + `context.jsonl`, so the graph the operator watches is the same graph the kernel will replay after cold start. Without the event-driven loop, the keyed tool row, and the scroll-anchor invariant, a live item graph would flicker, duplicate tool rows on every lifecycle event, and jump the viewport on every delta — destroying exactly the "transcript comprehension under live updates" (§X) that makes a branching session observable. This theme is the operator's eyepiece onto the sharded architecture; every other theme produces events this surface projects.

## Definition of done
- The render loop is event-driven off the monotonic notification cursor with a bounded idle backstop, draws only on dirty/input, and burns no CPU when idle; the durable-ledger reconciliation remains the cold-start-safe backstop (AGENTS.md §IV, §X).
- Every tool invocation occupies exactly one keyed row across its full lifecycle, including the theme-13 `killed_by` terminal classes (`cancelled`/`timeout`/`signal`/`exited`); `tool_requested`/`tool_completed` never produce a row (AGENTS.md §IV).
- Assistant deltas stream into one buffer with the operator's scroll anchor preserved while live output continues below, and the in-memory transcript is bounded with eviction backed by the append-only ledger (AGENTS.md §XIV "terminal scrollback under live streaming").
- Branch shards and delegated children render as a graph object (parent edge, status, converge edge), projected purely from `context.jsonl` + `events.jsonl` — no TUI-invented topology (theme 01/06).
- A raw-event inspector panel renders the typed envelopes at the cursor for debugging, bounded and ANSI-safe (AGENTS.md §XVIII item 10).
- The §XIV adversarial list (terminal scrollback under live streaming, same-millisecond event bursts, hostile stdout/stderr chunks) passes and gates promotion, with a native installed `%LOCALAPPDATA%\Vantari\bin\vantari.exe` proof on Windows.
- No speculative status bus, no second transcript in TUI memory, no append-per-lifecycle-stage row — the TUI remains a read model over `events.jsonl` (AGENTS.md §I, §IV).
