# 19 — Reference Pressure Loop

**Priority: P1**

## The seam

AGENTS.md §XVIII item 16 names this theme verbatim: *"Reference pressure loop: periodically re-harvest `.refs/openai__codex` and `.refs/badlogic__pi-mono`, but land only primitives that reduce VANTARI surface complexity while increasing runtime proof strength."* §XI (Reference Discipline) binds it with four rules: inspect the references *before intricate kernel changes*; *copy ownership patterns, not complexity*; borrow checkpoint boundaries, item lifecycle pressure, and context ownership; reject extension forests, branch graphs, and global session stores *until proven necessary*. And it states the gate every harvested idea must pass — the **VANTARI compression test**: *fewer concepts at the call site, stronger guarantees in the core, lower runtime ambiguity, clearer recovery evidence.*

The seam is that the harvest is, today, an *ad hoc, one-shot, memory-only* activity. Three reference clones exist (`.refs/openai__codex`, `.refs/badlogic__pi-mono`, `.refs/vercel__eve`) plus several secondary clones (`.refs/savageops__scion`, `.refs/withastro__flue`, `.refs/zf-main`, `.refs/KrillClaw-main`, `.refs/nullboiler-main`, `.refs/nullclaw-main`), a primary-source index (`.refs/sources/agent-harness-source-index.md`, 27 numbered sources S01–S27), and a shelf of dated harvest notes in `.docs/research/`. What does *not* exist is the closed loop: a schedule, a delta-detection step, a compression-test record, and a rejected-primitive archive. The harvest produces decisions; the decisions are not re-pressured against newer reference state.

The binding constraint is §XIII (Proof-Gated Promotion Lifecycle) and §XII (Forbidden Anti-Patterns). The reference pressure loop is itself a promotion gate applied to *imported* ideas: every borrowed primitive must clear *Recon → Contract → smallest durable slice → canonical tests → native installed proof* exactly like a kernel change, and the rejection protocol (*record the hypothesis, name the seam, keep the failed evidence, remove the code path, state the next mechanism*) is what populates the rejected-primitive archive. §XII's *"parallel systems for the same responsibility"* and *"broad rewrites driven by intuition"* are the two failure modes this loop exists to prevent: a harvest that imports a second event bus, a second transcript, or a hooks/plugin forest because a competitor has one.

Both are detected only by re-pressure.

## What the competitor does

### How mature engineering teams run continuous competitive/reference analysis

The industry pattern, distilled from the published playbooks ([Learning Loop — Competitive Analysis](https://learningloop.io/plays/competitive-analysis), [unkover — Competitive Analysis Framework](https://unkover.com/blog/competitive-analysis-framework/), [Parallel.ai — Automate Competitive Intelligence with APIs and AI Agents](https://parallel.ai/articles/how-to-automate-competitive-intelligence-with-apis-and-ai-agents), [AriseGTM — Competitive Intelligence Automation 2026 Playbook](https://arisegtm.com/blog/competitive-intelligence-automation-2026-playbook)), is a four-stage pipeline: **discovery → extraction → monitoring → enrichment.**

- **Discovery** — maintain a tracked roster of competitors/reference targets with a stated *reason each is on the list*. VANTARI already has this in `.refs/sources/agent-harness-source-index.md`; the gap is that the roster is not versioned against upstream commits.
- **Extraction** — pull the *artifact* (clone, essay, README, source) into a local, cite-addressable store. VANTARI has this in `.refs/<org>__<repo>/`.
- **Monitoring** — delta detection: signal when a tracked target changes. This is the stage VANTARI does *not* have. The published patterns automate it (AriseGTM's three tiers: Monitoring+Alerting, Pipeline+Enrichment, Full Autonomous); the VANTARI equivalent is a `git fetch` + `git log HEAD..origin` diff per reference clone, gated behind an explicit operator command, not a background daemon (§XII: *"background workers without cancellation, idempotent marks, measurable benefit, and cold-start reconciliation"*).
- **Enrichment** — the *decision* layer: what changed, what is transferable, what is the verdict. In product CI this is a human-readable brief; in VANTARI it is a dated harvest note in `.docs/research/` plus a compression-test record per candidate primitive.

The **discipline that distinguishes infrastructure competitive analysis from product marketing analysis** is the *falsifiable rejection*. A product team tracks competitor features to copy or counter them; an infrastructure team tracks competitor architectures to *reject most of them* with a named reason. Scion's transfer matrix (`.docs/research/2026-05-05-scion-harvest.md`) is the in-house exemplar: every primitive gets a verdict column, and *"reject"* is as valuable an outcome as *"adapt"* because it prevents a future re-litigation. This is the VANTARI loop's distinguishing property — the **rejected-primitive archive is a first-class output, not a side effect.**

### The 2026 agent-runtime landscape (re-harvest candidates)

The landscape has consolidated into three layers, each with transferable structure VANTARI has not yet pressured:

- **Agent frameworks (the loop + tool + memory layer):** [PydanticAI](https://pydantic.dev/docs/ai/core-concept/agent/) (type-safe structured outputs, typed dependencies), [DSPy](https://dspy.ai/tutorials/customer_service_agent/) (compiled/declarative prompts, metric-driven optimization), [Agno](https://github.com/agno-agi/agno) (lightweight multi-agent), [Mastra](https://mastra.ai) (TypeScript-native, filesystem-first agent-as-directory — the closest philosophical cousin to where Eve is heading), [CrewAI](https://docs.crewai.com/en/concepts/agents) (role-based crews, async kickoff), [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/) (minimalist successor to Swarm: handoffs, guardrails, tracing), [LangGraph](https://docs.langchain.com/oss/python/langgraph) (explicit state-graph orchestration, checkpointing, human-in-the-loop), [AutoGen v0.4 / AG2](https://github.com/microsoft/autogen) (event-driven conversational runtime). Comparison surveys ([Galileo](https://galileo.ai/blog/autogen-vs-crewai-vs-langgraph-vs-openai-agents-framework), [Composio](https://composio.dev/content/openai-agents-sdk-vs-langgraph-vs-autogen-vs-crewai), [Uvik 2026](https://uvik.net/blog/agentic-ai-frameworks/), [Bovo 2026](https://www.bovo-digital.tech/en/blog/12-most-powerful-ai-agent-frameworks-2026)) converge on one finding directly relevant to VANTARI: *the frameworks that win on runtime legibility model orchestration as an explicit, replayable state machine (LangGraph, OpenAI Agents SDK, Mastra), while those that model it as a conversation graph (AutoGen) or a role metaphor (CrewAI) optimize for ergonomics at the cost of recovery evidence.* VANTARI's ledger-native model is the far end of the same axis LangGraph and Mastra are moving toward.
- **Durable orchestration (the resume/retry/timeout layer):** [Inngest](https://www.inngest.com), [Trigger.dev v3](https://trigger.dev), [Hatchet](https://github.com/hatchet-dev/hatchet), [Temporal](https://temporal.io). Surveys ([PkgPulse 2026](https://www.pkgpulse.com/guides/hatchet-vs-trigger-dev-v3-vs-inngest-durable-workflows-2026), [Mordrel/Medium](https://medium.com/@matthieumordrel/the-ultimate-guide-to-typescript-orchestration-temporal-vs-trigger-dev-vs-inngest-and-beyond-29e1147c8f2d)) show the durable-execution primitives these systems sell — checkpoints, retries with backoff, step-level timeouts, idempotency keys, cancellation propagation — are the *same* primitives VANTARI's WAL+checkpoint+write-intent-ledger (themes 04, 09, 13) already encode natively. The transferable lesson is *not* the orchestration engine (Temporal/Inngest run a server; VANTARI is a single binary) but the **step-addressing and continuation-token discipline**: Hatchet and Trigger.dev name every step, make resumption idempotent by step key, and reconcile orphaned work at cold start. Eve's `reconcile-session-continuation-token.ts` and `turn-execution-cursor.ts` are the same idea inside an agent loop.
- **The coding-agent incumbents (the live competition):** Claude Code, Codex, Cursor, Windsurf, Cline, Aider, OpenHands, pi-mono — already reverse-engineered in `.docs/research/2026-07-15-agent-memory-competitor-harvest.md` (memory) and `.docs/research/2026-07-13-vantari-one-ix-agent-runtime-competition.md` (tool lifecycle/turn grammar). The [Vercel "we removed 80% of our agent's tools"](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools) essay (source S10) and the [Manus context-engineering post](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) (source S09) remain the two strongest external endorsements of VANTARI's subtractive thesis: *fewer tools, file-system-first, KV-cache-aware compaction.*

## Why VANTARI does it better

1. **The compression test is a gate, not a slogan.** Every other team's competitive loop asks *"what can we adopt?"* VANTARI's asks *"what can we adopt that reduces our surface complexity while raising our proof strength?"* — four falsifiable clauses (*fewer concepts at the call site / stronger guarantees in the core / lower runtime ambiguity / clearer recovery evidence*). A primitive that fails any clause is rejected with a recorded reason. This is why VANTARI's `.docs/research/` reads as a sequence of *rejections with evidence* (no second transcript, no vector DB, no background consolidator, no hook forest) rather than a feature backlogue copied from competitors. The loop makes the compression test repeatable instead of aspirational.
2. **The rejected-primitive archive prevents re-litigation.** Industry CI playbooks treat rejection as absence-of-adoption; VANTARI treats it as a *first-class artifact*. A dated record that says *"we looked at LangGraph's checkpoint graph on <date>, rejected it because it introduces a branch graph without a convergence owner (§XI), next mechanism to investigate is the shard ledger (theme 01)"* is worth more than a missing feature, because it stops the next harvester from re-opening the same question. This is the §XIII rejection protocol (*record the hypothesis, name the seam, keep the failed evidence, remove the code path, state the next mechanism*) applied to *imports*.
3. **Ledger-native beats framework-native.** LangGraph, Mastra, OpenAI Agents SDK, and the durable-execution engines all *add a layer* to get replayability: a state graph, a compiled agent directory, a workflow runtime, a continuation-token table. VANTARI's replayability is a *property of the substrate* — `messages.jsonl` is append-only, `context.jsonl` is sequence-addressed, `events.jsonl` is the evidence spine. The competitor adopts a framework to get what VANTARI has natively. So the pressure loop's default verdict on any framework primitive is *"we already have the ledger version; does the framework version reduce our call-site concepts?"* — and the answer is usually no.
4. **Delta detection is local and operator-gated, not a background daemon.** Eve and the durable-execution engines ship background reconciliation loops. VANTARI's pressure loop runs on demand: `git fetch` inside a reference clone, `git log` to produce a diff, a human reads the diff and writes a harvest note. This honors §XII (*no background workers without cancellation, idempotent marks, measurable benefit, cold-start reconciliation*) and §XVIII item 16's *"periodically"* — the cadence is milestone-driven, not always-on.
5. **One reference discipline, not many.** The 2026 landscape tries to be the framework, the runtime, the observability layer, and the deployment platform at once (Mastra ships an Inngest deployment; Inngest ships agent skills for Claude Code/Codex/Cursor; LangGraph ships its own checkpoint store and tracing). VANTARI's discipline is to harvest *one primitive at a time* from *one layer* and prove it through the canonical lane before considering the next. §XI: *copy ownership patterns, not complexity.*

### THE PRESSURE LOOP (target)

```text
  ┌──────────────────────────────────────────────────────────────────┐
  │  CADENCE: per major milestone, or when a reference clone's        │
  │           `git fetch` shows new commits on a watched path          │
  └──────────────────────────────────────────────────────────────────┘
   │
   ▼
 1. DETECT  — `git -C .refs/<ref> fetch && git log HEAD..origin -- <watched paths>`
             produces a delta. No delta ⇒ no harvest this cycle.
   │
   ▼
 2. EXTRACT — read the diff; list candidate primitives (one sentence each).
             write to `.docs/research/<date>-<ref>-reharvest.md`.
   │
   ▼
 3. PRESSURE — for each candidate, run the compression test (4 clauses):
              fewer call-site concepts? stronger core guarantees?
              lower runtime ambiguity? clearer recovery evidence?
              record verdict: ADOPT | DEFER | REJECT, each with a named seam.
   │
   ▼
 4. ARCHIVE — append the verdict + rationale to `.docs/research/_rejected-primitives.md`.
              REJECT is a first-class outcome. ADOPT enters the §XIII promotion lifecycle.
   │
   ▼
 5. LAND    — ADOPTed primitives follow Recon→Contract→slice→tests→installed proof.
             no primitive lands without clearing the compression test AND the promotion gate.
```

The watched-paths list is deliberately narrow: for `openai__codex`, watch `codex-rs/app-server`, `codex-rs/core/src/memories`, `codex-rs/rollout-trace`; for `badlogic__pi-mono`, watch `packages/agent/src`, `packages/ai/src`; for `vercel__eve`, watch `packages/eve/src/execution`, `packages/eve/src/harness`, `packages/eve/src/context`, `research/`. Everything outside the watched set is in scope only by an explicit decision to widen it.

## Pipeline items under this theme

### P1-19a: Re-harvest schedule + delta-detection command
- **Contract:** an operator-run `scripts/ref-pressure.sh` (and `.ps1` for §XV Windows-native) that, for each primary reference clone, runs `git fetch`, computes `git log --oneline HEAD..origin/<default> -- <watched paths>`, and prints a per-reference delta report: clone path, last-harvested commit (recorded in `.docs/research/_ref-state.json`), new commits since, and the watched paths that changed. No background process, no daemon, no network on the hot path — it runs when the operator runs it (§XII). No harvest is triggered automatically; the report is the trigger for a human decision.
- **Mechanism:** a small `scripts/ref-pressure.{sh,ps1}` plus a `.docs/research/_ref-state.json` ledger recording `{ "openai__codex": {"harvested_commit": "<sha>", "harvested_at": "<date>", "watched": [...]}, ... }` for each tracked reference. The script reads `_ref-state.json`, runs `git -C .refs/<ref> fetch`, diffs `harvested_commit..origin` over the watched paths, and emits the report. Updating `harvested_commit` happens only when a harvest note is written, so the state file tracks *pressure*, not *fetch*.
- **Test:** against a synthetic reference clone with a known new commit on a watched path, the script reports exactly that commit; with a new commit on an *unwatched* path, the script reports no delta; the `_ref-state.json` round-trips through `std.json` (or `jq`) and is stable across runs.
- **Proof:** running the script against the live `.refs/vercel__eve` clone reports the post-2026-08-04 commits that added `durable-session-store.ts`, `turn-workflow.ts`, and `research/anchored-thread-midturn-resume.md` — i.e. it detects the stale-harvest condition that already exists today.

### P1-19b: Compression-test checklist (the four-clause gate, recorded)
- **Contract:** every harvest note (new or re-harvest) ends with a **Compression-test record**: one block per candidate primitive, each primitive scored against the four clauses from §XI — *(1) fewer concepts at the call site, (2) stronger guarantees in the core, (3) lower runtime ambiguity, (4) clearer recovery evidence* — each clause answered *pass / fail / n-a* with a one-line justification, and a final verdict `ADOPT | DEFER | REJECT` with the named seam (which kernel file/domain it touches) and, if `REJECT`, the next mechanism to investigate (§XIII rejection protocol). A primitive lands only with four passes (or three passes + one documented `n-a`).
- **Mechanism:** a fixed markdown template appended to `.docs/research/_compression-test-template.md` and copy-pasted into each harvest note. No tooling — the discipline is human review against a fixed schema, because the judgment ("fewer concepts at the call site") is not automatable. The template is the contract; the dated harvest note is the proof.
- **Test:** back-fill the three highest-value existing harvests — Scion (`.docs/research/2026-05-05-scion-harvest.md`), the memory harvest (`.docs/research/2026-07-15-agent-memory-competitor-harvest.md`), and the ix/competition harvest (`.docs/research/2026-07-13-vantari-one-ix-agent-runtime-competition.md`) — with the four-clause record for their headline primitives, and confirm the recorded verdicts match the decisions already made (sticky-activity ADOPT, vector DB REJECT, background consolidator REJECT, typed turn grammar ADOPT-after-loop-extraction).
- **Proof:** a reader who was not present for the original harvest can reconstruct *why* a primitive was rejected from the compression-test record alone, without re-reading the competitor source.

### P1-19c: Rejected-primitive archive (first-class output)
- **Contract:** a single `.docs/research/_rejected-primitives.md` append-only ledger. Each entry: date, reference clone + source path, primitive name (one phrase), the compression-test verdict (the four clauses + `REJECT`), the named reason, and the named next mechanism. Examples to seed it: *LangGraph checkpoint graph (branch graph without convergence owner — §XI)*, *Scion Hub/Broker topology (hosted coordination before local multi-host problem is real)*, *Codex two-phase async memory consolidator (background machinery before synchronous memory proves value)*, *Claude Code hooks/plugin forest (multiple clients needed; VANTARI has one live backend lane)*, *Temporal/Inngest server engine (single-binary; ledger already durable)*, *Cline six-file Memory Bank (prompt-managed parallel state system)*.
- **Mechanism:** a dated, append-only markdown table. Entries are never deleted (a rejection may be revisited only by a new entry that supersedes it, citing the changed condition). This is the §XIII rejection protocol (*keep the failed evidence*) made durable and indexable.
- **Test:** the seeded entries each cite the harvest note that produced them; a grep for a primitive name finds both the harvest note (evidence) and the archive entry (verdict).
- **Proof:** the archive contains at least 10 seeded rejections on day one, each traceable to a dated harvest note, and any future harvester can grep it before re-opening a question.

### P2-19d: New-candidate harvest pass — the 2026 framework layer
- **Contract:** a single dated harvest note (`.docs/research/<date>-2026-framework-reharvest.md`) that pressures one transferable primitive from each of the strongest 2026 candidates against the compression test: **Mastra** (filesystem-first agent-as-directory — compare to VANTARI's session-as-directory under `.var/sessions/<id>/`), **LangGraph** (explicit state-graph checkpointing — compare to theme 01's shard ledger), **OpenAI Agents SDK** (handoff primitive + guardrails — compare to theme 05 tool governance + theme 06 delegation), **PydanticAI** (typed dependencies + structured outputs — compare to theme 03 typed events), **Hatchet/Trigger.dev continuation tokens** (step-key idempotency — compare to theme 04 durable execution + theme 09 write-intent ledger), **DSPy metric-driven compilation** (compare to theme 07 deterministic context compiler). ## North-star link

The north star (theme 01) is *"many windows, each a shard, that branch and converge."* The reference pressure loop is how VANTARI guarantees the shard ledger stays the *simplest possible* expression of that idea. Every competitor (Eve, LangGraph, Mastra, the durable-execution engines) is independently reinventing branch-and-converge under a framework layer; without a pressure loop, VANTARI risks either (a) importing a competitor's framework-shaped solution to a problem the ledger already solves, widening the call-site surface (compression-test clause 1), or (b) missing a primitive that would genuinely reduce ambiguity (clause 3). The loop keeps the ledger the substrate and the competitor the reference — never the other way around. It is also the loop that feeds every other theme: the typed turn grammar (03), durable execution (04), tool governance (05), delegation (06), byte-level integrity (17), and telemetry (18) each have a "what the competitor does" section that is only as good as the last harvest. A stale harvest degrades every theme's falsifiability; a re-pressured harvest keeps every "why VANTARI does it better" claim citeable to current evidence.

## Definition of done
- A re-harvest cadence is defined (per-major-milestone, or on watched-path delta) and documented; an operator-run `scripts/ref-pressure.{sh,ps1}` reports per-reference deltas against a `.docs/research/_ref-state.json` ledger, with no background daemon (AGENTS.md §XII).
- Every harvest note — new or re-harvest — terminates with a four-clause compression-test record (§XI) per candidate primitive, each clause pass/fail/n-a with justification, and an `ADOPT | DEFER | REJECT` verdict naming the seam and the next mechanism (§XIII).
- A rejected-primitive archive `.docs/research/_rejected-primitives.md` exists, is append-only, and is seeded with at least the headline rejections already established (LangGraph branch graph, Scion Hub/Broker, Codex async memory, Claude Code hooks forest, Temporal/Inngest server engine, Cline Memory Bank).
- The 2026 framework layer (Mastra, LangGraph, OpenAI Agents SDK, PydanticAI, Hatchet/Trigger.dev, DSPy) has a dated pressure pass; the stale Eve harvest (post-2026-08-04 durable-session additions) has a dated re-harvest that re-evaluates theme 01's "Eve has no sharded model" finding.
- No harvested primitive lands in the kernel without clearing both the compression test (§XI) and the proof-gated promotion lifecycle (§XIII); rejected primitives are archived, not silently dropped.
- The discipline is ledger-native and single-binary: no second transcript, no second event bus, no background harvester, no imported orchestration framework — the loop exists to keep it that way.
