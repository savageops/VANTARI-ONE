# 14 — C ABI Acceleration Socket

**Priority: P2 (proof-gated, deferred)**

## The seam

AGENTS.md Section XVIII item 5 names a narrow `extern` boundary — a C ABI acceleration socket — as a frontier option, *only after profiling identifies a real bottleneck*. Candidate domains: tokenizer probes (exact token counting), SIMD search (JSONL scanning, needle matching), JSONL scanning (parsing performance for large transcripts), and terminal width/grapheme kernels.

This theme is intentionally the last in the frontier pipeline. It is the only theme whose entire purpose is to *forbid* itself until evidence demands it. The Mechanical Cost Model (Section X) is the gate: before adding any native primitive, name which cost center it lowers. If the answer is "organization" or "we might need it later", the code stays local. A dynamic worker or native kernel is admissible only when it calls the same proven primitive as the scalar path and adds measurable capability beyond scheduling (Section VIII).

The socket is not an architecture. It is a *promotion channel*: scalar Zig code that is measurably hot gets an optional `extern` twin behind the same contract, compiled in only when the profiling harness proves the cost.

## What exists today

All four candidate domains are today implemented in pure scalar Zig, with no C interop, no `export fn`, no SIMD, and no external native dependency. The build (`apps/backend/build.zig`) links only the Zig standard library plus the `vantari_tui` (vaxis) module at the executable boundary; the `VAR1` library module is explicitly dependency-free.

- **Tokenizer probe (heuristic).** Token estimation is `(chars + 3) / 4` — `apps/backend/src/core/context/budget.zig:4-7` (`estimateText`), reused by the compactor at `apps/backend/src/core/context/compactor.zig:244-263` (`estimateMessages`, `estimateText`, `estimateChars`). There is no exact tokenizer and no model-specific BPE.
- **JSONL scanning (whole-file + line parse).** Every read path loads the entire file into memory via `fsutil.readTextAlloc` (`std.fs.cwd().readFileAlloc`), then splits on `\n` and calls `std.json.parseFromSlice` per line. See `readSessionMessages`/`readSessionMessagesFromPath`, `readEvents`, and the reverse tail-scan in `readLatestContextCheckpoint` (`apps/backend/src/core/sessions/store.zig:280-355, 526-530`).
- **Needle search.** Content search is not native at all — it is delegated to the external `iex` subprocess (`apps/backend/src/core/tools/builtin/search_files.zig:70-77`, `argv` of `iex search --json`). There is no in-process SIMD search kernel.
- **Terminal width / grapheme kernels.** TUI row counting is byte-oriented, not grapheme-aware: `wrappedSegmentTake` walks raw bytes and breaks on ASCII space (`apps/backend/src/clients/tui_chat.zig:1291-1300`); `introVisualWidth` uses `std.unicode.utf8CountCodepoints` (`tui_chat.zig:1245-1247`), which counts codepoints, not display columns — wide CJK/emoji characters are under-counted. The vaxis `Unicode` handle (`tui_chat.zig:1949`) is used by `TextInput`, not by the transcript wrapping path.
- **Profiling harness.** There is none. Timing today is limited to wall-clock `std.time.milliTimestamp()` stamps on session/tool lifecycle records (`apps/backend/src/core/executor/loop.zig:307,371,389`; `apps/backend/src/core/agents/service.zig:221,233,264`). No code measures context-compile latency, JSONL scan latency, event-replay latency, or terminal frame-render latency.

Two latent inefficiencies are already visible without a harness, and both are *algorithmic* before they are instruction-level:

1. `nextSessionMessageSeq` (`store.zig`, called on every `appendSessionMessage`/`appendContextCheckpoint`) reads, fully JSON-parses, and heap-allocates **every** message in `messages.jsonl` solely to compute `max(seq) + 1`. The fix is a tail scan or a persisted high-water mark — pure Zig, no native code.
2. `readLatestContextCheckpoint` already does the right thing (reverse tail-scan for the last valid line) but still `readTextAlloc`s the whole `context.jsonl` first. A bounded tail read would lower the same cost center without any ABI change.

Both are evidence that the first bottleneck is the algorithm, not the instruction stream — exactly the distinction AGENTS.md Section X enforces.

## What the competitor does

**Eve** (`packages/eve/src/harness/token-estimate.ts`) ships an 11-line tokenizer: `JSON.stringify(value).length / 4`. The comment is explicit — *"Good enough for deciding whether compaction is needed; the real token count comes back from the model each step via `CompactionConfig.lastKnownInputTokens`."* The ground truth is the provider's `usage` block (`packages/eve/src/shared/token-usage.ts`: `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`). `getInputTokenCount` (`compaction.ts:36-53`) stacks the heuristic on top: `prior + estimateTokens(messages.slice(priorCount))`. There is no native acceleration, no SIMD, no exact tokenizer, no C ABI surface anywhere in the Eve harness.

**Codex** (`codex-rs/`) is the strongest test of the "everyone reaches for tiktoken" assumption. Its Rust core has **no** text tokenizer: a repository-wide search for `tiktoken`, `cl100k_base`, `o200k_base`, or a `count_tokens`/`Tokenizer` struct in `codex-rs/` returns only OAuth/JWT `token_data.rs` and base64 `.encode(...)` calls — not BPE. Like Eve, Codex relies on the provider's reported usage for real token counts and applies structural truncation for context management rather than exact local counting. The Python `tiktoken` library exists in the wider OpenAI ecosystem, but the Codex *agent core* does not embed it.

**pi-mono** (`packages/ai/`) likewise carries no local tokenizer. Its `total-tokens.test.ts` documents the model: `totalTokens` is computed from provider-native fields (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`), assembled per-provider in `packages/ai/src/providers/anthropic.ts:476-481`. There is no native/napi/simd path in the agent package.

**Industry primitives (reference only).** simdjson achieves 2–6 GB/s NDJSON throughput via SIMD, roughly 3–4x the best scalar parsers (Lemire et al., "Parsing Gigabytes of JSON per Second"). The official `tiktoken` is Rust-over-Python FFI; community notes (r/learnrust, users.rust-lang.org) record that per-call FFI crossing and `bytes`→`&[u8]` conversion can negate Rust's speed advantage for small, frequent calls — the boundary wants batching. For Zig, the consensus is that `std.mem.Allocator` is a vtable fat pointer and a Zig-only type: it cannot cross a `callconv(.C)` boundary, so the idiomatic socket is an opaque context handle plus paired `alloc`/`free` exports, with `extern struct` reserved for ABI-stable data (ziggit.dev, ncmiller.dev, antonz.org).

## Why VANTARI does it better

VANTARI's advantage on this theme is not "we have native code and they do not" — it is the *discipline* of refusing native code until the cost model names a hot path. The competitors' shared posture (heuristic-only or provider-usage-only, forever) is the failure mode AGENTS.md Section XII forbids ("broad rewrites driven by intuition instead of a named state transition or measured bottleneck") run in reverse: a broad *non-rewrite* driven by the assumption that nothing is ever hot.

1. **Cost-model-gated, not novelty-gated.** Every candidate native primitive must answer Section X's "Required Question" against a named cost center (context compile, tool dispatch, command run, TUI frame, session recovery). "Faster JSON" is not an answer; "context-compile JSONL scan exceeds N ms at M transcript rows, measured" is. Eve, Codex, and pi-mono never establish this measurement, so their heuristic is frozen by default.
2. **Algorithm before instruction.** The two latent inefficiencies above (`nextSessionMessageSeq` full-parse-for-max, whole-file `readTextAlloc`) prove that the first win is algorithmic and pure-Zig. The cost model forces this order: a SIMD JSONL scanner is inadmissible while the scan path still parses the whole file to find one integer. Native code arrives only after the scalar path is already optimal for its algorithm.
3. **Same contract, optional twin.** The socket is a promotion channel, not a parallel system (Section XII: "parallel systems for the same responsibility" is forbidden). The native primitive must expose the *same* contract as the scalar path — same inputs, same outputs, same allocator ownership rules — behind a build-time switch. The scalar path stays canonical; the native path is a measured opt-in. This is the structural form of Section VIII's "a dynamic worker is admissible only when it calls the same proven primitive."
4. **Opaque-handle ABI discipline.** When a native twin is admitted, the boundary follows the proven Zig pattern: `callconv(.C)` exports, `?*anyopaque` context handle, `extern struct` for ABI-stable data, paired `alloc`/`free` exports so the same runtime that allocates reclaims. No `std.mem.Allocator` crosses the boundary; the caller passes a caller-owned buffer or receives a handle it must release. This keeps the kernel dependency-free by construction (`build.zig`), with the native module an exe-level concern like vaxis today.

## Pipeline items under this theme

### P2-14a: Local performance telemetry harness (the gate)
- **Contract:** an operator command (e.g. `vantari perf`) that measures and prints low-noise counters for the six Section X cost centers: context compile (JSONL scan + checkpoint selection + provider payload bytes), tool dispatch, command run, TUI frame (event replay + wrap + render), session recovery, and provider turn. Counters are off by default and gated behind the explicit command; they never run in the hot path of a normal turn.
- **Mechanism:** `std.time.Instant`/monotonic timers wrapped around the existing scalar paths in `context/builder.zig`, `sessions/store.zig`, `executor/loop.zig`, `clients/tui_chat.zig`. No new runtime lane — the probes instrument the canonical code paths in place. Output is a typed report (count, min/mean/max/p99 per stage) over a configurable repetition count, deterministic enough to diff between builds.
- **Test:** the harness runs against a fixture transcript of N rows and asserts that (a) every measured stage is non-zero, (b) the measurement itself does not alter the stage's output (the compiled window is byte-identical with and without probes), and (c) a deliberately pathological input (e.g. 50k-row `messages.jsonl`) surfaces a measured scan cost that a small input does not.
- **Proof:** a checked-in `perf` report snapshot for a representative fixture, plus the cold-start replay proving the instrumented path produces the same provider payload as the uninstrumented path. This item is the gate: **none of P2-14b/c/d/e may start until this harness exists and names a hot path.**

### P2-14b: Exact tokenizer probe (conditional on P2-14a)
- **Contract:** only admissible if P2-14a proves the `(chars+3)/4` heuristic misclassifies a real provider window by more than an agreed threshold (e.g. >15% delta vs provider `usage.input_tokens` on a captured corpus), *and* that misclassification causes a measurable failure (premature compaction, overflow, or wasted tokens). If proven, add a build-time-optional C ABI probe (`extern fn vantari_tokenize_count(handle, text_ptr, text_len) callconv(.C) u64`) backed by a proven tokenizer core (tiktoken-rs or HuggingFace tokenizers) wrapped behind an opaque handle.
- **Mechanism:** the probe is a promoted twin of `budget.estimateText`, not a replacement. The scalar `estimateText` stays the default; the probe is selected by a build flag and a per-session policy. FFI is batched (count a whole message array in one crossing, never per-token) to avoid the per-call overhead documented for Python↔Rust tiktoken bindings.
- **Test:** a corpus of real provider payloads where heuristic vs exact differ by >threshold; the probe's count matches the provider `usage.input_tokens` within tolerance; and a falsification case proving the scalar path is still used when the probe is off (no silent native dependency in the default build).
- **Proof:** the discrepancy corpus checked in, the build-time-off default proven (`build.zig` produces no native linkage without the flag), and the provider-payload parity evidence. Rejection protocol (Section XIII) applies in full if the discrepancy does not reproduce.

### P2-14c: SIMD JSONL scanner (conditional on P2-14a)
- **Contract:** only admissible if P2-14a proves JSONL scan latency is a measured bottleneck *after* the algorithmic fixes (tail-scan for `nextSessionMessageSeq`, bounded tail read for `readLatestContextCheckpoint`) have landed in pure Zig. simdjson-class throughput (2–6 GB/s) is irrelevant if the transcript is KB–MB scale; the gate is measured scan time at the harness's pathological fixture size, not theoretical GB/s.
- **Mechanism:** if admitted, a `callconv(.C)` scanner export that takes a caller-owned `[*]const u8` + length and returns line offsets or parsed record handles via a paired `free` export. The scalar `splitScalar('\n')` + `parseFromSlice` path stays canonical; the SIMD path is a build-time opt-in twin behind the same read contract.
- **Test:** the SIMD twin returns byte-identical parsed records to the scalar path on the adversarial JSONL suite (torn trailing writes, BOMs, invalid UTF-8, duplicate seqs — the Section XIV pressure set); and the scalar path is proven still-active when the build flag is off.
- **Proof:** `perf` harness showing the scan cost drop on the pathological fixture, plus record-level parity evidence against the scalar reader. Rejection applies if the algorithmic fixes alone closed the gap.

### P2-14d: Terminal width / grapheme kernel (conditional on P2-14a)
- **Contract:** only admissible if P2-14a proves TUI frame render is a measured bottleneck *and* the current byte-based wrapping produces a visible correctness defect (mis-wrapped CJK/emoji rows under live streaming). If proven, replace `wrappedSegmentTake`/`introVisualWidth` with a grapheme-cluster + East-Asian-Width-aware column counter — first as pure Zig (Unicode tables are data, not native code), promoted to a native twin only if the Zig column counter itself shows up as hot.
- **Mechanism:** the column counter is a pure-data Unicode width table behind the existing `messageRowCount` contract. The vaxis `Unicode` handle already in `tui_chat.zig:1949` is the reference for grapheme segmentation; the work is wiring the transcript wrap path to it, not writing a new kernel.
- **Test:** a transcript with wide characters (CJK fullwidth, emoji ZWJ sequences) wraps to the correct display-column count, not the codepoint or byte count; scroll math under live streaming stays correct; and the frame-render cost is measured before and after by P2-14a.
- **Proof:** visual parity evidence (wrapped rows match a reference terminal) plus the `perf` measurement showing whether the data-table path is itself hot enough to warrant a native twin. Most likely outcome: pure-Zig Unicode tables close the correctness gap, and no native code is needed — which is the correct proof-gated result.

### P2-14e: Socket contract (the ABI shape, lands only with the first admitted twin)
- **Contract:** the first time any of P2-14b/c/d is admitted, land the narrow socket contract that all subsequent twins share: a `callconv(.C)` export surface, `?*anyopaque` context handle created/destroyed by paired exports, `extern struct` for any data crossing the boundary, caller-owned buffers for inputs, paired `alloc`/`free` exports for any output the caller must release. No `std.mem.Allocator` crosses the boundary.
- **Mechanism:** a single `apps/backend/src/core/abi/` owner (kernel-owned capability domain per Section IX) holding the export declarations, the handle lifecycle, and the build-time switch in `build.zig`. The native module is an exe-level dependency, exactly like `vantari_tui` today; the `VAR1` library module stays dependency-free.
- **Test:** the socket is exercised by whichever twin triggered it (14b/c/d), with a falsification case proving the default build links no native object. A second twin added later must reuse the same handle lifecycle without duplicating it.
- **Proof:** `build.zign` default target links zero native objects; the flag-enabled target links exactly the admitted twin; cold-start replay and the Section XV Windows-native installed-binary proof both pass on the flag-enabled build.

## North-star link

The north star (01) is token-minimal sharded windows. Native acceleration is the *last* lever for that goal, not the first: the economic engine is the shard ledger (01), token-minimal compilation (02), and the deterministic context compiler (roadmap item 7). A native tokenizer probe only matters if the heuristic misclassifies shard windows; a SIMD scanner only matters if compiling a shard window is scan-bound. This theme exists to ensure that if and when scalar Zig cannot keep a shard cheap or a frame correct, there is a *measured, contracted, ABI-disciplined* path to a native twin — and that until then, the discipline of refusing it is itself the advantage. The profiling harness (P2-14a) is the only unconditional item; it is also the engine for Section XVIII item 15 (local performance telemetry).

## Definition of done
- The profiling harness (P2-14a) exists, is off by default, instruments the six Section X cost centers through the canonical code paths, and produces a diffable report on a checked-in fixture.
- No native primitive (14b/c/d) is admitted until the harness names its cost center with a measured number at a pathological input size, and the algorithmic pure-Zig fix has already landed where one exists.
- Any admitted native twin is a build-time opt-in behind the shared socket contract (P2-14e), with the scalar path proven still-canonical in the default build and byte/record-identical output proven against the twin.
- The default Windows-native installed binary (`%LOCALAPPDATA%\Vantari\bin\vantari.exe`, Section XV) links zero native acceleration objects; the flag-enabled build passes the same installed-binary proof.
- If the harness proves no bottleneck, the rejection protocol (Section XIII) is recorded and this theme stays deferred — which is a successful outcome, not a failure.
