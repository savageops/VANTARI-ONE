# 22 — Adversarial Pipeline Test Mesh

**Priority: P0**

## The seam

AGENTS.md §XIV states the contract verbatim: *"Tests must behave like adversarial pipeline probes."* It then names thirteen probes every suite must exercise — corrupted JSONL suffixes, stale running sessions, failed no-prompt resumes, invalid tool batches, orphan tool results, duplicate context after provider overflow, command timeout and process locks, stdout/stderr cap markers, oversized write payloads, cwd escape before process launch, same-millisecond event bursts, terminal scrollback under live streaming, and installed binary auth/workspace resolution. §XIII makes tests gate 2 of the proof-gated promotion lifecycle: *"Tests cover the user-visible pipeline and at least one falsification pressure case."* §XVIII item 13 names the deep pipeline test mesh as a frontier item: *"adversarial suites for provider recovery, tool loops, context rebuilds, TUI event consumption, installed auth/workspace resolution, and Windows process behavior."*

The governing principle, also from §XIV: *"A passing test is valuable only when the assertion proves an invariant a shallow implementation would violate."* A test that a shallow implementation passes is not a probe — it is decorative. This theme owns the discipline that turns the existing 1346 test functions into a coherent adversarial mesh: each of the thirteen probes is a named, mechanical assertion that a naive implementation (silent `catch continue`, positional array rebuild, timestamp-cursor ordering, in-memory-only state, full-file rewrite) would fail.

This theme is explicitly **not** a new test framework, a new test runner, or a parallel harness. The substrate already exists: the mock transports in `runtime_loop_test.zig`, the verify-switch in `agent_pipeline_deep_matrix_test.zig`, the in-process transport in `provider_test.zig`, and the isolated temp roots in `workspace_resolution_test.zig`. This theme completes the mesh — closes the probes that today have no dedicated assertion (same-millisecond ordering, terminal scrollback, TUI event consumption, installed-binary auth/workspace), hardens the existing probes into property form, and wires the whole mesh to gate promotion on the installed Windows binary.

## What the competitor does

### Vercel Eve — AppHarness + mock-model + Temporal-backed durability

Eve ships a first-class test harness (`packages/eve/src/internal/testing/`):

- **`app-harness.ts` / `app-harness.integration.test.ts`** — `createTestRuntime({ agent })` returns a runtime with a *scoped session*. The integration test (`app-harness.integration.test.ts:35`) asserts "compiled artifacts scoped to the test runtime session": before `run` the session has no artifacts, inside `run` `getActiveRuntimeSession() === runtime.session`, and after `run` the process-default session never saw the test artifacts. A second test (`:57`) runs two concurrent runtimes (`tenant-a`, `tenant-b`) and asserts "isolates two concurrent test runtimes without cache crosstalk." This is the tenant-isolation probe.
- **`mocks/mock-model.ts`** — a declarative mock model descriptor; `mockModel({ id })` delegates to an auto-activated mock adapter (`shouldMockAuthoredRuntimeModels()`) that provides "deterministic behaviour (weather tool calls, skill load calls, bootstrap replies)" without further wiring. The mock is process-wide under `NODE_ENV=test`.
- **`durable-session-workflow.ts`** — a workflow test-time fixture exercising `createDurableSessionState` / `readDurableSession` round-trip *inside a real workflow runtime*. Crucially it includes `durableSessionWriteWithRetryStep` (`:62`): on `meta.attempt === 1` it throws an intentional failure, and the test verifies "the retry's returned state, not the seed state, is what the next read sees." This is Eve's equivalent of the §XIII "keep the failed evidence" rejection protocol — encoded as a retry probe.
- **`compact-session.test.ts`** — thin: `createCompactFn` is tested by mocking the entire `Runtime` interface with `vi.fn()` and asserting the channel-local token is namespaced (`slack:C1:T1`) and the runtime result is passed through. The compaction *invariant* (no orphaned tool result, no prefill rejection) is not asserted here — it is asserted inside the AI SDK's `splitMessagesForCompaction`, which Eve does not own.
- **`structural-tests/`** — `file-length.test.ts` and `runtime-boundary.test.ts` enforce structural invariants over the source tree (file length limits, module boundary rules) rather than runtime behavior.

**Limitations directly relevant to the test mesh:** (1) Eve's mock model is process-global and auto-activated — there is no per-test adversarial transport that injects overflow-then-success, refusal, or malformed tool-call shapes; determinism comes from a canned weather/skill script, not from a probe that a shallow implementation would fail. (2) The harness delegates durability to a vendored Temporal Workflow World (`.eve/.workflow-data`) — the test mesh never has to prove torn-write or cold-start recovery itself, because Temporal owns it. VANTARI's premise is one binary, zero runtime dependencies, so the mesh must prove recovery directly. (3) The compaction test mocks the entire runtime surface and asserts only routing; the structural invariants (orphan skip, duplicate-context-after-overflow) are left to the upstream AI SDK.

### OpenAI Codex — rollout-trace: observe first, interpret later

Codex ships a dedicated `rollout-trace` crate (`codex-rs/rollout-trace/README.md`). Its relevance to the test mesh is the *reducer-invariant* discipline, which is the closest published analogue to §XIV's "assertion proves an invariant":

- **Strict reducer invariants.** *"raw events are replayed in `seq` order; payload files must exist before events refer to them; reduced object IDs are stable within one replay; model-visible conversation is derived from model-facing payloads, not from runtime convenience output; runtime payloads are evidence, not proof that the model saw the same bytes."* These are the five properties a reducer test must falsify.
- **Best-effort, never-fatal.** *"Rollout tracing must never make a Codex session fail just because diagnostic recording failed."* The trace layer degrades gracefully — but it is *opt-in diagnostic* (`CODEX_ROLLOUT_TRACE_ROOT`), not the canonical execution ledger. It does not gate recovery or context compilation.
- **`app-server-test-client/`** — a test client for the app-server protocol, the closest thing to an end-to-end probe harness.

**Limitations:** (1) `rollout-trace` is a *post-hoc replay* tool, not an adversarial probe generator. It helps debug a failure after the fact; it does not inject overflow, refusal, torn writes, or cancellation to *find* the failure. (2) The README specifies the spine *shape* (`seq`, payload externalization, replay order) but publishes no contract for the thirteen §XIV probes — those are left to whatever writes the JSONL, and Codex offers no adversarial suite for them. (3) Codex's inline Rust tests (`login/src/auth/*_tests.rs`) cover auth storage in isolation; there is no published deep-pipeline matrix that sweeps provider-recovery × tool-loop × context-rebuild in one suite.

### badlogic pi-mono — real-provider e2e + SSE/overflow/abort probes

pi-mono's `packages/ai/test/` is the richest provider-probe set among the competitors, and it runs against *real* providers (resolved OAuth tokens at module level):

- **`context-overflow.test.ts` / `overflow.test.ts`** — generates Lorem-ipsum content sized to `contextWindow + 10000` tokens (`targetTokens * 4 * 1.5` char estimate) and asserts every provider returns either `stopReason: "error"` with an overflow message *or* succeeds with `usage.input > contextWindow`. The invariant is `isContextOverflow()` returns `true` for all providers — a cross-provider contract probe.
- **`anthropic-sse-parsing.test.ts`** — feeds a hand-built `createSseResponse` of `event:`/`data:` lines including a *malformed tool JSON delta* (`partial_json` with an unescaped backslash and tab) and asserts the parser repairs it. This is the torn-SSE-chunk probe done at the JSON-repair layer.
- **`abort.test.ts`** — streams a response, calls `controller.abort()` after 50 chars of text, and asserts `msg.stopReason === "aborted"` and `msg.content.length > 0`. This is the process-cancellation probe.
- **`agent/test/e2e.test.ts`** — end-to-end agent loop.

**Limitations:** (1) The overflow and SSE probes run against real network providers, so they are non-deterministic, credential-gated, and cannot run in CI without rate-limit/secret management — they are *integration smoke tests*, not mechanical invariants. (2) The probes assert provider-level behavior (`stopReason`, `usage`), not durable-transcript behavior — pi-mono does not verify that a session resumed after overflow has no duplicate context, because its canonical writer is a full `_rewriteFile` (theme 17's finding), so there is no append-only invariant to probe. (3) No published adversarial suite for stale sessions, orphan tool results, or installed-binary resolution.

### Industry substrates

- **Temporal — time-skipping, activity mocking, workflow replay.** Temporal's `TestWorkflowEnvironment` ([docs.temporal.io](https://docs.temporal.io/develop/go/best-practices/testing-suite)) provides three primitives directly applicable to an agent-runtime mesh: (1) *time skipping* — `workflow.Sleep` and timers fast-forward so long-running workflows complete in seconds; (2) *activity mocking* — `OnActivity`/`OnActivityByName` replace activity implementations with deterministic mocks; (3) *workflow replay* — workflow code is replayed deterministically against an event history to verify correctness. The determinism rule is strict: no direct clock access, no randomness, no I/O inside the workflow — the test framework enforces it. The gotcha is real: a mocked activity that throws can *hang* the test ([community.temporal.io](https://community.temporal.io/t/throwing-exception-in-mocked-activity-hangs-the-test/10932)) if the mock does not match the retry policy. VANTARI's equivalent is the mock-transport pattern already in `runtime_loop_test.zig` — but Temporal's *replay against recorded history* is the primitive VANTARI's mesh does not yet have: a recorded `events.jsonl` spine replayed through the executor to verify determinism.
- **Property-based testing in Zig — `std.testing.fuzzInput` + ZlowCheck.** Zig's stdlib ships a fuzzer whose corpus unification with unit tests is tracked in [ziglang/zig#25352](https://github.com/ziglang/zig/issues/25352). ZlowCheck ([ziggit.dev](https://ziggit.dev/t/zlowcheck-a-model-testing-library-to-integrate-with-zig-s-fuzzer/10053)) is a model-based/property-based library that integrates with Zig's built-in fuzzer; its data generators act as de-serializers for the fuzzer. The property-based discipline ([blog.nelhage.com](https://blog.nelhage.com/post/property-testing-like-afl/), [jo3-l.dev](https://jo3-l.dev/posts/proptest/)) treats a property test as a constrained fuzzer: generate random valid-prefix-plus-random-corruption inputs and assert the parser either recovers the valid prefix or fails safely. This is the exact shape the §XIV "corrupted JSONL suffix" probe wants — and it is native to Zig, no new dependency.
- **Chaos engineering — fault injection, not green-screens.** Netflix's Chaos Monkey ([sei.cmu.edu](https://www.sei.cmu.edu/blog/devops-case-study-netflix-and-the-chaos-monkey/), [gremlin.com/chaos-monkey](https://www.gremlin.com/chaos-monkey)) runs continually and *randomly terminates instances* to test resilience. The transferable principle is fault injection: a probe does not assert the happy path, it injects a fault (process kill, partial write, mid-stream abort) and asserts the system reaches a defined terminal state with evidence. VANTARI's equivalent is the adversarial transport (`mockSendOverflowThenSuccess`, `mockSendToolLoopOverflowThenSuccess`) — but Chaos Monkey's *randomized, continual* injection is the discipline the mesh needs for the thirteen probes: a probe runner that randomly selects one of the thirteen faults per trial and asserts the recovery invariant.
- **SSE parsing edge cases — chunk-boundary, terminator-variant, trailing-flush.** The published SSE-parser bug class is narrow and specific ([github.com/praxis-proxy/ai#7](https://github.com/praxis-proxy/ai/issues/7), [github.com/diggerhq/opencomputer#301](https://github.com/diggerhq/opencomputer/issues/301)): (1) chunks split mid-line, mid-field, mid-delimiter must be reassembled; (2) CRLF, LF, and mixed terminators are all valid; (3) a trailing event without a terminating `\n\n` must be flushed or it is silently dropped; (4) rapid-succession malformed events. VANTARI's `provider reconstructs split SSE data fields instead of dropping first visible token` covers (1); (2)–(4) are not named probes.

## Why VANTARI does it better

1. **Probes assert invariants, not happy paths.** Eve's `compact-session.test.ts` mocks the entire runtime and asserts routing; pi-mono's overflow test asserts `stopReason` against a real network provider. VANTARI's `loop rebuilds provider payload after tool overflow without duplicating durable tool context` (`runtime_loop_test.zig:1253`) asserts `countOccurrences(payloads[2], "role:tool") == 1` and `countOccurrences(payloads[2], "READ_RESULT_SENTINEL") == 1` — a shallow implementation that duplicates the tool result after rebuild would pass Eve's routing assertion and fail VANTARI's. The §XIV principle ("a passing test is valuable only when the assertion proves an invariant a shallow implementation would violate") is the selection criterion for every probe in this theme.
2. **One adversarial transport, many injected faults — not a process-global mock.** Eve's `mockModel` is auto-activated process-wide and serves a canned deterministic script. VANTARI's transport is a per-test function pointer (`transport.sendFn`) with a captured context struct (`OverflowRetryContext`, `ToolLoopContext`, `CancelContext`), so each probe injects a *different* fault shape (overflow-then-success, tool-loop-overflow-then-success, cancel-on-first-check, resume-prompt) against the *real* executor, real session store, and real ledger writers. The fault is scoped to the test; the recovery path under test is production code.
3. **Recovery proven against the durable ledger, not in-memory state.** pi-mono asserts `stopReason`; VANTARI asserts `context.jsonl` contains `provider_overflow` *and* the rebuilt payload has exactly one tool result *and* the session record on disk is `cancelled` *and* the latest event is `session_cancelled`. The assertion reads back from the append-only ledgers (`messages.jsonl`, `context.jsonl`, `events.jsonl`) — the same path cold-start replay takes. A test that only inspects in-memory state cannot prove cold-start correctness; VANTARI's probes do.
4. **Thirteen named probes, thirteen named owners — no decorative coverage.** The gap table above shows eight probes covered, three partial, two absent. This theme gives every probe a Contract (the invariant), a Mechanism (the code seam), a Test (the assertion a shallow implementation fails), and a Proof (the installed-binary gate). No probe is "we have a test with that word in the name"; each is a mechanical falsification of a naive implementation.
5. **Temporal's replay primitive, ledger-native.** Temporal replays workflow code against recorded event history to verify determinism. VANTARI's equivalent is replaying a recorded `events.jsonl` spine through the executor — but because the spine *is* the append-only ledger (not a Temporal-external workflow store), the replay test reads the same bytes cold-start reads. No external workflow engine, no vendored durability layer.
6. **Property-based fuzzing native to Zig.** The §XIV "corrupted JSONL suffix" probe is currently one hand-written case. Zig's `std.testing.fuzzInput` and ZlowCheck turn it into a property: generate a random valid prefix, append a random corruption, assert the reader returns the valid prefix and surfaces the tear. The fuzzer is part of the toolchain ([ziglang/zig#25352](https://github.com/ziglang/zig/issues/25352)) — no new dependency, no external corpus.

## Pipeline items under this theme

### P0-22a: Same-millisecond event burst ordering (seq breaks ties over `created_at_ms`)
- **Contract:** when two events share `created_at_ms` (real on fast machines, guaranteed under load), the reader returns them in monotonic `seq` order, not timestamp-string order. `events.jsonl` `seq` is the tiebreaker; `created_at_ms` is informational. AGENTS.md §XIV "same-millisecond event bursts." §IV rejects the timestamp-cursor model (Eve's `logs-events.ts` sorts by `at` string via `localeCompare`) precisely because it is non-deterministic under bursts.
- **Mechanism:** the event reader (`readEvents`, `store.zig:318`) already splits on `\n`; add an assertion that the returned slice is sorted by `seq` ascending and that a `created_at_ms` collision does not reorder. This requires `seq` on `events.jsonl` (theme 12 P0-12b); until then, the probe asserts the transcript's `nextSessionMessageSeq` tiebreaker (`store.zig:821`) and the event-read order is stable. The probe seeds two events with identical `created_at_ms` and distinct `seq` and asserts order.
- **Test (AGENTS.md §XIV item 11):** seed an `events.jsonl` with three frames where frames 2 and 3 share `created_at_ms = 123456789` but `seq` = 2, 3; assert `readEvents` returns them in `seq` order and that swapping the byte order of frames 2 and 3 in the file still yields `seq`-ascending output (the reader does not trust file position when `seq` disagrees). A shallow implementation that sorts by `created_at_ms` string fails this probe.
- **Proof:** adversarial suite runs the same-millisecond probe and passes on the installed Windows binary.

### P0-22b: Stale running session reconciliation on cold start
- **Contract:** on cold start, a session whose persisted status is `running` but whose owner process is no longer alive (crash, kill, machine restart) is reconciled: the stale owner is detected, the session is marked `failed` with a typed `failure_reason` (e.g., `stale_owner`), and a reconciliation event is emitted. The session is not silently resurrected, nor silently left `running` forever. AGENTS.md §XIV "stale running sessions"; §XV "Process supervision must account for Windows handle lifetime." §XVI names this "stale owner reconciliation," not "session cleanup."
- **Mechanism:** the cold-start path scans `.var/sessions/*/status` for `running` sessions, probes the owning PID/handle liveness (Windows `OpenProcess`/`WaitForSingleObject`, POSIX `kill(pid, 0)`), and for each stale owner writes `setSessionStatus(.failed)` + `failure_reason = "stale_owner"` + a `session_reconciled` event. This is theme 04 P0-4c's reconciliation surface; this item owns the *probe*, not the mechanism.
- **Test (AGENTS.md §XIV item 2):** seed a session record with `status = running` and a PID that does not exist (or a sentinel the reconciler treats as dead); run cold-start reconciliation; assert the persisted status is `failed`, `failure_reason == "stale_owner"`, and the latest event is `session_reconciled`. A shallow implementation that ignores stale owners (or silently resets them to `running`) fails this probe.
- **Proof:** cold-start reconciliation runs against a fixture with three stale `running` sessions and produces three `session_reconciled` events; the suite passes on the installed Windows binary.

### P0-22c: Failed no-prompt resume fails closed with provider-visible evidence
- **Contract:** when a child/delegated session is resumed with no ability to issue a fresh prompt (the parent is gone, the resume transport cannot re-prompt), the resume *fails closed*: the session reaches `failed` with a `failure_reason` that names the no-prompt condition, and the failure is visible in the event ledger so the parent (if it ever returns) can read why. The resume does not hang, does not synthesize a phantom prompt, does not silently succeed. AGENTS.md §XIV "failed no-prompt resumes."
- **Mechanism:** the executor's resume path (`runPromptWithOptions` with `session_id` set, `runtime_loop_test.zig:742`) currently requires a prompt; the probe exercises the branch where the transport's resume-prompt function returns an error (simulating "cannot re-prompt"). The executor must translate that into `Error.ResumeFailed` (or equivalent) and persist `status = failed` + `failure_reason = "no_prompt_resume"` + a `session_failed` event. This is the negative-pressure counterpart to Eve's `durableSessionWriteWithRetryStep` — but where Eve asserts the retry succeeds, VANTARI asserts the *un-retryable* failure is durable and visible.
- **Test (AGENTS.md §XIV item 3):** pre-create a child session, provide a resume transport whose `sendFn` returns `error.CannotReprompt`; invoke resume; assert the call returns a typed error, the persisted status is `failed`, `failure_reason` names the no-prompt condition, and `session_failed` is the latest event. A shallow implementation that retries forever, synthesizes a prompt, or returns `running` fails this probe.
- **Proof:** adversarial suite runs the failed-no-prompt-resume probe and passes on the installed Windows binary.

### P0-22d: stdout/stderr cap marker on truncation (typed, not silent)
- **Contract:** when a tool's stdout or stderr exceeds `max_output_bytes`, the captured output is truncated *and* a typed cap marker is appended (e.g., `[output truncated at N bytes; M bytes lost]`) so the provider and the operator can see truncation happened. The truncation is not a silent drop. AGENTS.md §XIV "stdout/stderr cap markers." §XVI names this "bounded stdout/stderr deltas," not "tool ran."
- **Mechanism:** the shell_exec output capture (`tools_test.zig:1086` asserts cap deltas are forwarded) gains an assertion that the forwarded delta ends with a recognizable cap marker when truncation occurred, and that the marker carries the byte count. The existing `shell_exec clamps command limits before runner dispatch` (`:1183`) and `tool error envelope summarizes oversized failed arguments` (`:664`) are the adjacent probes; this item owns the *stdout/stderr* cap specifically.
- **Test (AGENTS.md §XIV item 8):** invoke `shell_exec` with a command that emits `max_output_bytes + 4096` bytes on stdout; assert the captured delta length is `<= max_output_bytes`, the delta ends with the typed cap marker, and the marker string contains the lost-byte count. ### P1-22f: Property-based fuzz harness for the JSONL readers
- **Contract:** the four ledger readers (`readEvents`, `readSessionMessagesFromPath`, `readLatestContextCheckpoint`, `readLatestEvent`) satisfy a property: for any valid prefix of N frames followed by arbitrary corruption, the reader returns exactly the N valid frames (byte-identical content) and surfaces a reconciliation signal for the corruption. The property holds across random valid-prefix lengths, random corruption offsets, random corruption byte patterns (truncation, byte-flip, invalid-UTF-8 injection, BOM injection, duplicate-seq injection). AGENTS.md §XIV "corrupted JSONL suffixes" as the canonical property.
- **Mechanism:** a Zig fuzz entry using `std.testing.fuzzInput` ([ziglang/zig#25352](https://github.com/ziglang/zig/issues/25352)) — or a model-based generator via ZlowCheck ([ziggit.dev](https://ziggit.dev/t/zlowcheck-a-model-testing-library-to-integrate-with-zig-s-fuzzer/10053)) — that interprets the fuzz input as (valid-prefix-length, corruption-type, corruption-bytes), builds a `messages.jsonl` in a temp dir, runs the reader, and asserts the valid-prefix property. This is the property-based generalization of `verifyPoisonedCheckpointSuffixIgnored` (one hand-written case) into the full QuickCheck/Hypothesis form ([blog.nelhage.com](https://blog.nelhage.com/post/property-testing-like-afl/)). It composes with theme 17's frame-CRC and quarantine sidecar.
- **Test (AGENTS.md §XIV item 1, property form):** the fuzz harness runs for a configured corpus budget and asserts zero property violations; a regression corpus of known-tricky inputs (BOM-prefixed, mid-frame byte-flip, duplicate-seq, torn tail) is checked in as seed inputs. A shallow implementation with `catch continue` fails the property on the first byte-flip case.
- **Proof:** the fuzz harness runs in CI on the installed Windows binary and reports zero violations over the configured budget.

### P1-22g: Adversarial mock provider (overflow, refusal, malformed tool-call shape)
- **Contract:** a single mock provider transport that can be programmed per-test to emit, in sequence: (a) context-overflow then success (already in `mockSendOverflowThenSuccess`), (b) a provider refusal (stop reason `refusal`), (c) a malformed tool-call shape (tool call with no `id`, with an unknown `name`, with unparseable `arguments_json`), (d) a tool-call batch that exceeds the per-turn tool budget, (e) a mid-stream SSE disconnect. - **Mechanism:** generalize the existing `OverflowRetryContext`/`ToolLoopContext` pattern (`runtime_loop_test.zig`) into a `ScriptedTransport` that takes an ordered list of fault descriptors and a captured-context struct. This is Eve's `mockModel` done adversarially: instead of a canned deterministic script, each test scripts a *fault sequence* and asserts the recovery invariant. The malformed-tool-call-shape probe is the negative counterpart to `loop executes tool calls and exposes descriptors in the provider payload` (`:1042`).
- **Test:** for each fault class, one probe asserting the correct terminal state and ledger evidence: overflow→retry-once→checkpoint; refusal→`failed` with `failure_reason = "provider_refusal"`; malformed tool call→provider-visible repair evidence (composes with `loop turns malformed shell_exec arguments into provider-visible repair evidence`, `:1105`); budget-exceeding batch→`Error.ToolBudgetExceeded`; mid-stream disconnect→`failed` with partial deltas persisted. - **Proof:** the scripted-transport suite runs on the installed Windows binary; each fault class has a passing probe.

## North-star link

The north star (theme 01) branches a session into many context windows and converges them; each shard is replayable only if its ledger survives every fault in §XIV's thirteen-probe list. A shard whose checkpoint was duplicated after provider overflow (probe 6) is a corrupt shard; a shard whose resume failed silently with no prompt (probe 3) is an abandoned shard with no evidence; a shard whose events reorder under a same-millisecond burst (probe 11) is a shard whose replay is non-deterministic. The adversarial mesh is the falsification layer that proves the shard graph is trustworthy: every probe is a fault a naive shard implementation would suffer, and every probe's assertion is the invariant that makes the shard cold-start-replayable. Themes 03 (typed event grammar), 04 (durable execution), 12 (binary-safe event spine), 13 (interruptible process supervision), and 17 (byte-level session integrity) all land their canonical tests *into* this mesh — this theme owns the discipline that those tests are probes, not decorations.

## Definition of done
- All thirteen §XIV adversarial probes have a named owner, a named verify function, and a passing assertion that a shallow implementation would violate.
- Same-millisecond event bursts are ordered by `seq`, not `created_at_ms`; the probe seeds a collision and asserts monotonic output (P0-22a).
- Stale `running` sessions are reconciled to `failed` with `failure_reason = "stale_owner"` and a `session_reconciled` event on cold start (P0-22b).
- Failed no-prompt resumes fail closed with provider-visible evidence in the ledger; no hang, no phantom prompt, no silent success (P0-22c).
- stdout/stderr truncation emits a typed cap marker naming the lost-byte count; no silent truncation (P0-22d).
- Command timeout terminates the process tree and records post-kill evidence; locked binaries produce a typed diagnostic, not an obscure file-lock error (P0-22e).
- The JSONL readers satisfy the valid-prefix property under property-based fuzzing across random corruption (P1-22f).
- A scripted adversarial transport covers overflow, refusal, malformed tool-call shape, budget-exceeding batch, and mid-stream disconnect (P1-22g).
- TUI scrollback under live streaming renders in `seq` order with no frame loss or duplicate, including out-of-arrival-order events (P2-22h).
- The §XV installed-binary gate is automated: the real `%LOCALAPPDATA%\Vantari\bin\vantari.exe` resolves auth, workspace, and health in a clean process (P2-22i).
- Every probe reads back from the durable ledger (the same bytes cold-start reads), not from in-memory state alone.
- No second test framework, no parallel harness — the mesh extends the existing `verify*` switch, the existing mock transports, and the existing isolated temp roots.
