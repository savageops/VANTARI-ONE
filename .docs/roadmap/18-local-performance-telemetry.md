# 18 — Local Performance Telemetry

**Priority: P1**

## The seam

AGENTS.md §XVIII item 15 names this theme verbatim: *"Local performance telemetry: measure token compilation, JSONL scan, event replay, terminal frame render, process spawn, and tool dispatch latencies with low-noise counters gated behind explicit commands."* §X defines the **Mechanical Cost Model** — six mechanisms, each with a cost center and a *required question* — and ends with the directive: *"before adding abstraction, name which cost center it lowers."* This theme is the closed loop that makes that directive falsifiable: every counter this theme ships is named after a cost-center row, and every measurement exists to answer that row's required question with a number, not a vibe.

The binding constraint is §VIII: *"Health, readiness, and diagnostics stay thinner than capability. They expose enough state to operate the system; they do not become a parallel product."* And §XII forbids *"Diagnostics fatter than the capability being diagnosed."* So telemetry here is not a tracing product, not a remote exporter, not a second event bus. It is a fixed-memory counter register, read out on demand by an operator command, that answers the six cost-center questions locally — in-process, on the same binary the operator is already running, with zero per-measurement allocation and zero background threads.

The seam is narrow on purpose. AGENTS.md §XVI's calibration applies: say *"context-compile latency histogram, 8 power-of-two buckets, no allocation on the hot path,"* not "perf metrics." "Fast" is not a unit; this theme ships the unit.

## What exists today

- **One duration measurement, one cost center, one granularity.** The executor loop is the only place that computes a duration. `renderToolFinishedEvent` (`apps/backend/src/core/executor/loop.zig:804`) derives `duration_ms: i64 = @max(@as(i64, 0), finished_at_ms - started_at_ms)` (`loop.zig:812`) from two `std.time.milliTimestamp()` reads at `loop.zig:371` and `loop.zig:389`, then writes it into the `var1.tool_finished.v1` event JSON (`loop.zig:817/830/842`). This covers exactly the **Tool dispatch** cost center, and only at millisecond granularity.
- **Timestamps exist, but as record fields, not as measurements.** `std.time.milliTimestamp()` is called across the codebase (`agents/service.zig:137,221,264,347,432,525`; `sessions/store.zig:98,223,241,258`; `context/compactor.zig:83,266`; `evaluation/events.zig:38,70,97`; `auth/store.zig:258`; `auth/openai_codex.zig:296`), but every call stamps a record (`created_at_ms`, `updated_at_ms`, `timestamp_ms`, `expires_at_ms`). None of them bracket a region to measure its duration. The clock primitive is in hand; the measurement discipline is not.
- **The context compiler has no timing at all.** `context/builder.zig` — the **Context compile** cost center, AGENTS.md §X's required question *"Is the window built once through the compiler and replayable after cold start?"* — performs `readLatestContextCheckpoint`, `appendCompactedMessages`, `appendRawMessages`, `readSessionMessages`, and the pending-tool-result synthesis with zero timers around any of them. There is no number anywhere that says how long a window takes to build, how long the JSONL scan inside it takes, or how the cost grows with transcript length.
- **No provider stream timing.** The **Provider turn** cost center asks *"Does the operator see deltas before terminal output?"* The provider adapters (`providers/openai_compatible.zig`, `providers/anthropic.zig`, `providers/dispatch.zig`) reconstruct SSE deltas and tool calls but record no time-to-first-delta, no stream-parse duration, no tool-call-reconstruction latency. The cost center's required question is answered today only by eyeballing the terminal.
- **No event-replay or terminal-frame timing.** The **TUI frame** cost center asks *"Does the interface preserve transcript comprehension under live updates?"* `clients/tui_chat.zig` polls progress events (`tui_chat.zig:271`, `std.Thread.sleep(progress_poll_ms * std.time.ns_per_ms)`), formats rows (`formatProgress`, `:1590`), and queries the terminal (`:799`, `std.time.ns_per_s`) — but measures neither the replay pass nor the render pass. The **Session recovery** cost center (*"Can a dead process leave the next client with truthful state?"*) has no cold-start-replay timer.
- **No `stats` / `profile` command surface.** The CLI command list (`clients/cli.zig:459-617`) is `run`, `continue`/`sessions`, `workspace`, `config`, `health`, `schedule`, `serve`, `kernel-stdio`, `tools`, `models`. `health` (`cli.zig:520`, help at `:336`) is a thin readiness check — *"does not send a model completion request"* — that prints `status: ready` plus model/workspace/auth fields (`cli.zig:867`). It exposes no latency, no counter, no histogram. The HTTP bridge mirrors this as `GET /api/health` (`host/http_bridge.zig:297`). There is no operator command that answers any cost-center question with a measured number.

**Gap:** AGENTS.md §X names six cost centers with required questions. Today, one of the six (Tool dispatch) has a duration number, at millisecond granularity, embedded in an event and not aggregated. The other five — Provider turn, Context compile, Command run, TUI frame, Session recovery — have no measurement at all. The Mechanical Cost Model is, against the current code, a table of questions with one partial answer.

## What the competitor does

### Vercel Eve — OpenTelemetry span product, remote exporters, process-global config

Eve builds telemetry as a **productized OpenTelemetry tracing layer**, not a local counter register. The entire path is OTel-native and export-oriented:

- **Process-global instrumentation config, registered once at server startup.** `instrumentation-config.ts:39` `registerInstrumentationConfig` stores the authored `InstrumentationDefinition` on `globalThis` under `Symbol.for("eve.harness-instrumentation-config")` so the Nitro instrumentation plugin and the bundled harness chunk share one source of truth despite being two distinct ESM module instances. The harness reads it at turn time (`tool-loop.ts:506` `getInstrumentationConfig()`) to decide whether telemetry is on.
- **Per-turn OTel span, opened on first step.** `tool-loop.ts:510` `trace.getTracer("eve")`; `:532` `turnSpan = tracer.startSpan("ai.eve.turn", { attributes })`. The span carries framework attributes (`eve.version`, `eve.environment`, `eve.session.id`, `ai.telemetry.functionId`). Continuation steps restore the parent OTel context (`resolveStepOtelContext`) so AI SDK spans nest as children (`tool-loop.ts:540`). The turn id is set mid-flight (`:733` `turnSpan.setAttribute("eve.turn.id", ...)`).
- **Telemetry is threaded as an AI SDK parameter on every model call.** `enrichTelemetry` (`tool-loop.ts:254`) builds a `TelemetryOptions` (`isEnabled: true`, `recordInputs/recordOutputs`) and passes `telemetry:` into `streamText`/`generateText` at `:618`, `:813`, `:1051`. The AI SDK then emits its own `ai.*` spans as children of `ai.eve.turn`.
- **Remote exporters are the default sink.** The docs registry ships first-class integrations for Honeycomb, Datadog, Arize, Jaeger, Sentry, and Raindrop (`apps/docs/registry/instrumentation/*`). The local span spool (`.eve/traces/v1/<traceId>/segments/`, one immutable OTLP/JSON file per span) is the *defensive* layer, not the operator surface; the operator surface is a TUI trace viewer (`cli/dev/tui/traces/trace-store.ts`) that reads the spool and renders the span tree.
- **Authored runtime context is merged beneath reserved framework keys.** `instrumentation-runtime-context.ts` `buildTelemetryRuntimeContext` always emits `eve.session.id`, `eve.turn.id`, `eve.step.index`, `eve.turn.sequence`, `eve.version`, `eve.environment`, `eve.channel.kind`; authored resolver output is merged underneath, and reserved `eve.*` keys are dropped from user input so the framework keys stay authoritative.

**Limitations directly relevant to VANTARI:** (1) **Allocation overhead on the hot path.** OTel spans allocate — span objects, attribute maps, the `runtimeContext` record built per call. The Go OTel SDK's own issue ([open-telemetry/opentelemetry-go#5410](https://github.com/open-telemetry/opentelemetry-go/issues/5410)) reports *"GC doubled and throughput declined by 40%, largely coming from the overhead of allocating additional memory for the spans and attributes."* Eve runs on a GC'd V8 runtime where this is absorbed; VANTARI's premise is a single no-GC Zig binary where per-turn allocation is the exact cost §XVIII item 6 (arena/quota discipline) exists to control. (2) **Remote-first, not local-first.** Eve's sink is an exporter; the operator needs Honeycomb/Datadog/Jaeger running to see a span. VANTARI's operator has one binary and no collector. (3) **It is a parallel product.** Eve's telemetry has its own config system, its own file format (`.eve/traces/v1`), its own TUI viewer, its own Nitro plugin, its own docs registry. This is exactly the *"parallel product"* §VIII forbids and the *"diagnostics fatter than capability"* §XII forbids. (4) **Span tree, not cost-center rows.** Eve's `ai.eve.turn` span answers *"what happened in this turn"*; it does not map one-to-one onto AGENTS.md §X's six cost centers with their required questions. The mechanical cost model has no representation in Eve's telemetry.

### OpenAI Codex — rollout-trace (opt-in diagnostic) + auth-env telemetry

- **`rollout-trace` is an opt-in diagnostic spine, not the canonical ledger.** Codex ships a dedicated crate whose `trace.jsonl` is *"append-only raw events ordered by writer-assigned seq"* and is *enabled via `CODEX_ROLLOUT_TRACE_ROOT`* — it is explicitly not the execution ledger that gates recovery (theme 17 quotes the README verbatim). *"Rollout tracing must never make a Codex session fail just because diagnostic recording failed."*
- **Auth-env telemetry is metadata, not timing.** `login/src/auth_env_telemetry.rs` collects `AuthEnvTelemetry` (provider env-key name, codex-api-key-env-enabled flag) and exports it via `codex_otel::AuthEnvTelemetryMetadata` — it is descriptive attribution for an OTel export, not a latency measurement. The `codex-rs/otel` directory is a README only (no `src/`); there is no in-tree OTel SDK.

**Limitations:** (1) Codex's performance instrumentation is *opt-in and off the canonical path* — exactly the design that keeps diagnostics thinner than capability, but it also means Codex has no always-on local answer to its own cost centers. (2) The `rollout-trace` README specifies the spine *shape* (`seq`, payload externalization, replay order) but is silent on duration measurement — it records *what happened*, not *how long it took*. VANTARI's cost-model questions ("does the operator see deltas before terminal output?") have no Codex equivalent.

### badlogic pi-mono — no dedicated timing layer

pi-mono (`packages/agent`, `packages/ai`) has no performance-counter or timing layer of its own. Latency is not measured anywhere in the session manager or provider paths; the only "telemetry" hits are external provider SDKs and OTel vendored transitively through AI-SDK-style dependencies. There is no local read-out command. This is the negative space VANTARI fills: pi-mono has no answer to any cost-center question, local or remote.

### Industry substrates — fixed-bucket histograms, low-noise counters, Zig timing

- **HDR Histogram — power-of-two buckets, preallocated arrays, zero per-observation allocation.** ([github.com/HdrHistogram/HdrHistogram](https://github.com/HdrHistogram/HdrHistogram)) The high-dynamic-range histogram uses powers-of-two top-level buckets with a fixed number of sub-buckets, all preallocated at construction. Recording a value is a bucket-index computation and an array increment — no allocation, no locking, suitable for a hot path. This is the canonical fixed-memory latency distribution.
- **Prometheus cumulative histograms — predefined buckets, quantile interpolation.** ([prometheus.io/docs/practices/histograms](https://prometheus.io/docs/practices/histograms/)) When a requested percentile falls between two buckets, Prometheus assumes uniform distribution within the bucket range ([oneuptime.com](https://oneuptime.com/blog/post/2026-01-30-prometheus-histogram-bucket-design/view)). The lesson for VANTARI: a small fixed bucket set plus interpolation is enough to answer "what's the p95 of context compile" without storing every sample.
- **OTel's own overhead is the cautionary tale.** The Go SDK's measured 2× GC / 40% throughput loss ([opentelemetry-go#5410](https://github.com/open-telemetry/opentelemetry-go/issues/5410)) is the strongest empirical argument for a no-allocation counter register over a span-allocating tracer in a hot loop. The OneUptime/Coroot mitigation guidance — *"traces need to be sampled, metrics have minimal overhead"* ([HN discussion](https://news.ycombinator.com/item?id=44290331), [coroot.com](https://coroot.com/blog/opentelemetry-for-go-measuring-the-overhead/)) — is the industry arriving at the conclusion VANTARI starts from: counters, not spans, belong on the hot path.
- **Zig's timing primitives are sufficient and Windows-caveated.** The standard pattern is `const timer = std.time.Timer.start() catch unreachable; ... const elapsed_ns: u64 = timer.read();` ([cookbook.ziglang.cc/03-01-elapsed-time](https://cookbook.ziglang.cc/03-01-elapsed-time/), [mtsoukalos.eu](https://www.mtsoukalos.eu/2025/11/computing-elapsed-time-in-zig/)). Two Windows-native gotchas apply directly to VANTARI (§XV): `std.time.Timer` includes OS suspend time ([ziglang/zig#11175](https://github.com/ziglang/zig/issues/11175)), so long-running turn timers can be skewed by sleep/suspend; and `nanoTimestamp` has lower precision on Windows than on Linux ([ziglang/zig#22460](https://github.com/ziglang/zig/issues/22460)), so `Timer` (which uses `QueryPerformanceCounter` on Windows) is preferred over `nanoTimestamp` for duration measurement. For sub-microsecond regions, run the target repeatedly and average ([pyk.sh](https://pyk.sh/blog/2025-12-07-bench-fixing-microbenchmark-accuracy-in-zig)).

## Why VANTARI does it better

1. **Counter register, not span tree.** Eve allocates a span per turn, threads `TelemetryOptions` through every model call, and exports to a remote collector. VANTARI's telemetry is a fixed array of counters — one per cost-center row — each a power-of-two histogram of 8–10 preallocated buckets. Recording a measurement is a `bucket_index = leading_zeroes(elapsed_ns)` and an `@atomicRmw` increment. No allocation, no GC, no exporter, no collector, no second process. The thing §VIII forbids — *"they do not become a parallel product"* — is the thing Eve built.
2. **Cost-center-addressed, not turn-addressed.** Eve's `ai.eve.turn` span answers *"what happened in this turn."* VANTARI's counters are named one-to-one after AGENTS.md §X's six rows: `provider_turn`, `context_compile`, `tool_dispatch`, `command_run`, `tui_frame`, `session_recovery`. The Mechanical Cost Model is the schema; the required question in column three is the read-out label. This is the closed loop §X demands — *"name which cost center it lowers"* becomes *"read the counter for that cost center."*
3. **Low-noise by construction, opt-in by command.** The counters are always resident (a few hundred bytes total) but only read out when the operator runs `VAR1 stats`. They are not emitted to a log, not appended to a ledger, not streamed over the bridge — the measurement never reaches a writer. This is the opposite of Eve's per-turn span, which is exported on every turn whether anyone reads it or not. The Codex `rollout-trace` instinct (*"never make a session fail because diagnostic recording failed"*) is honored by making recording a single atomic increment that cannot fail.
4. **Local-first, single-binary.** Eve needs Honeycomb or Jaeger to make a span visible. VANTARI's operator runs `VAR1 stats` on the same installed `%LOCALAPPDATA%\Vantari\bin\vantari.exe` they are already running (§XV). The answer to *"does the operator see deltas before terminal output?"* is a number printed in the terminal the operator is already looking at.
5. **No new event grammar.** Eve invents a telemetry config system, a runtime-context merge layer, a span-spool file format, and a TUI viewer. VANTARI adds one command (`stats`) that prints pre-aggregated counters, and optionally one optional per-region timing field on the existing typed event schema (theme 03). No new file, no new ledger, no new bus, no new docs registry.
6. **Windows-native timing discipline.** `std.time.Timer` (not `nanoTimestamp`) is the duration source, because `Timer` uses `QueryPerformanceCounter` on Windows and sidesteps the `nanoTimestamp` precision defect ([zig#22460](https://github.com/ziglang/zig/issues/22460)). Turn-spanning timers (provider turn, command run) are reconciled against wall-clock `milliTimestamp` to absorb suspend-time skew ([zig#11175](https://github.com/ziglang/zig/issues/11175)). This is the §XV discipline applied to the clock.

```text
six cost-center counters, each a fixed power-of-two histogram:

read-out: `VAR1 stats` prints, per counter: count, p50/p95/p99 bucket, max-seen, last-seen-ns

```

The existing `tool_finished.duration_ms` (`loop.zig:812`) is preserved verbatim — it becomes one input to the `tool_dispatch` counter, downcast from ms to ns bucketing, with no change to the event schema.

- **Contract:** a `Counters` struct holding six power-of-two latency histograms (one per §X cost center), each a fixed `[10]u64` bucket array with `bucket_min_ns`/`bucket_max_ns` bounds and `count`/`max_seen_ns`/`last_seen_ns` scalars. Recording is a single `@atomicRmw(.Xchg, ...)` or atomic increment; read-out copies the array under a single atomic snapshot. No allocation on the record path. - **Mechanism:** new `apps/backend/src/core/diag/counters.zig`. Bucket index from `std.math.log2_int` of the elapsed-ns value (the HDR power-of-two scheme, [HdrHistogram](https://github.com/HdrHistogram/HdrHistogram)). One process-global `Counters` instance, sized ~300 bytes total. No writer thread; the register is passive. This is the substrate every other item in this theme records into.

## North-star link

The north star (theme 01) branches a session into many context windows and converges them. Every branch is a **Context compile** (the compiler builds the shard's window from the checkpoint + branch input) and every convergence is a **Provider turn** (the parent reprocesses the merge). If those two cost centers are unmeasured, the operator cannot tell whether sharding makes the system faster or slower — they can only feel it. Theme 18 is what makes "each shard is a fresh, cheap context window" a falsifiable claim: the `context_compile` counter answers *"how long does one shard's window take to build, and does it stay flat as the transcript grows?"* and the `provider_turn` counter answers *"does the operator see the merge deltas before the terminal moves?"* — which are the §X required questions, in the §XVI calibrated phrasing, with units. Without this theme, the sharded model ships on vibes; with it, every cost-center assertion in themes 01–17 is answerable with a number read off the same binary the operator is already running.

- A fixed-memory counter register exists, one histogram per §X cost center, zero allocations on the record path, no writer thread, no exporter, no second file format (AGENTS.md §VIII, §XII).
- All six cost centers (Provider turn, Context compile, Tool dispatch, Command run, TUI frame, Session recovery) record latency into the register via `std.time.Timer` brackets on their canonical regions; the existing `tool_finished.duration_ms` is preserved as input to the Tool-dispatch counter.

- Optional per-region `timings_ns` on the event schema (P2-18d) is additive, env-gated, default-off, and byte-identical to today when off; legacy readers parse it by ignoring the unknown field.
- The installed `%LOCALAPPDATA%\Vantari\bin\vantari.exe` (§XV) prints a populated `stats` table after a real `run`, and the table's rows map one-to-one onto AGENTS.md §X.
