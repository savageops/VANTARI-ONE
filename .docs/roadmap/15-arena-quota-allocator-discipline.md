# 15 — Arena/Quota Allocator Discipline

**Priority: P1**

## The seam

AGENTS.md §X prices "Context compile" against "JSONL scan, checkpoint selection, **allocation**, provider payload bytes" and §XVIII item 6 names the frontier directly: "split allocators by turn, provider payload, tool result, and UI frame." Allocation is a named cost center, not an implementation detail. Yet today the entire backend — CLI, TUI, stdio-RPC host, executor loop, context builder, provider adapter, tool runtime, agent service — runs off **one** allocator: `std.heap.page_allocator`, handed down from `apps/backend/src/main.zig:7,21,24,32,36` as an opaque `std.mem.Allocator` to every function in the call graph.

A `page_allocator` is correct for booting a process, but it is the wrong primitive for a long-running agent kernel because it has **no scope, no bound, and no leak signal**. Every `dupe`, every `allocPrint`, every `ArrayList.append`, every `std.json.parseFromSlice` either becomes the caller's manual `defer allocator.free(...)` burden (there are 634 such sites in `apps/backend/src/`) or it leaks. The seam this theme owns is the **allocation scope**: a named, owned, lifetime-bounded region of memory with a declared cap, such that the kernel can answer three questions at every turn boundary — *who owns this allocation, when does it die, and how big is it allowed to get?* Without those answers, "deterministic memory behavior: no unbounded growth, no leak across turns, no OOM mid-session" (AGENTS.md §XVIII item 6) is aspirational, not enforced.

This theme is distinct from but serves every other frontier item: theme 01 (shards) needs per-shard memory that dies on convergence; theme 03 (typed events) allocates per-event JSON that must not outlive the frame; theme 05 (tool effect receipts) must bound tool-result bytes; theme 10 (TUI workbench) must reset per render frame; theme 12 (delegation) must isolate child-turn memory from the parent. The allocator discipline is the substrate that makes those scopes cheap and provable instead of conventional and hoped-for.

## What exists today

- **One allocator rules them all.** `main.zig` calls `std.heap.page_allocator` six times and threads it as `std.mem.Allocator` into `cli.main`, `tui_chat.main`, and `tui_chat.mainContinueLatest`. No `ArenaAllocator`, no `GeneralPurposeAllocator`/`DebugAllocator`, no `c_allocator` appears anywhere in production code — grep of `apps/backend/src/` finds `ArenaAllocator` only inside `core/providers/models.zig` test blocks (6 sites, all `std.testing.allocator`-backed). Every other module receives `allocator: std.mem.Allocator` and frees by hand.

- **The turn scope is the executor function.** `runPromptWithOptions` (`core/executor/loop.zig:93-134`) owns the per-turn `messages` list — `var messages = std.array_list.Managed(types.ChatMessage).init(allocator)` — and tears it down with `defer { for (messages.items) |message| message.deinit(allocator); messages.deinit(); }`. This is the de-facto turn arena, except it is not an arena: it is a grown `ArrayList` of individually-heap-allocated `ChatMessage` structs, each freed one at a time, on the `page_allocator`, with no cap on `messages.items.len` across `max_steps` iterations (`loop.zig:177`). The list grows every step (`messages.append` at `:252`, `:308`, `:359`, `:419`, `:452`, `:459`, `:464`, `:471`) and is rebuilt in place by `rebuildProviderBaseMessages` (`loop.zig:556-592`) which clones every preserved message (`cloneChatMessage`, `loop.zig:597`) — a transient **doubling** of turn memory during every compaction.

- **The provider payload scope is `completeWithTransportAndHooks`.** `core/providers/openai_compatible.zig:184-202` allocates `url`, `payload`, and `response_body` as three independent `page_allocator` slices freed with three `defer allocator.free(...)` lines, then hands `response_body` to `parseCompletionResponse` (`:239-264`) which allocates `tool_calls` and `dupe`s `model`/`content` — also on the page allocator, also freed individually by the caller (`loop.zig:255` `defer completion.deinit(allocator)`). A single provider turn therefore touches the global allocator at least six times for transient buffers that all share one obvious lifetime.

- **The tool-result scope has a byte cap but no spill.** `core/tools/runtime.zig:419-489` (`runCommandWithLimitsPortable`) and `:562+` (Windows) hand each pipe to a `PipeCollector` that caps `output.items.len` at `max_output_bytes` and emits a one-shot `cap_reached` marker, then keeps reading and discarding (`runtime.zig:544-548`). The cap is correct, but the discarded bytes are **lost** — there is no `fullOutputPath` spill. `shell_exec` clamps `max_output_bytes` to `[1, 65536]` per stream (`builtin/shell_exec.zig:57,106`), so a 10 MB build log becomes 16 KB. The tool returns `[]u8` on the page allocator; the executor `dupe`s it into a `ChatMessage` (`loop.zig:419`) and frees the original — another transient doubling per tool call.

- **The UI-frame scope is the whole session.** `clients/tui_chat.zig` stores `ChatState.messages: std.ArrayList(Message)` (`:56`) and `seen_progress_events: std.ArrayList([]u8)` (the dedup set) on `self.allocator` (the page allocator from `main`). Both grow for the lifetime of the process: every `assistant_delta`, every `tool_output_delta` (each decoded from base64 at `:1552`), every progress key (`:360`) is `dupe`d and appended. `buildTranscriptRows` (`:1075`) allocates a fresh `ArrayList(TranscriptRow)` per render frame and frees it after — the one place a per-frame scope already exists, but it is hand-managed, not an arena, and the source `messages` list it reads from is unbounded.

- **The host allocates per-request jobs on the page allocator.** `host/stdio_rpc.zig:328` does `const job = try std.heap.page_allocator.create(RequestJob)` per inbound frame and `:480` `defer std.heap.page_allocator.destroy(job)` — a hand-rolled request scope with no quota and no leak detection if the worker thread detaches (`:335 thread.detach()`) and never reaches the destroy. `core/agents/service.zig:42,173-176` does the same for `WatchJob`, duping `workspace_root` onto the page allocator.

**Gap — four invariants are missing, each a real failure mode the current code admits:**

1. **No turn arena, so compaction doubles memory.** `rebuildProviderBaseMessages` (`loop.zig:564-592`) clones every preserved message into a fresh list, frees the old list, then appends — peak transient allocation is `2 × live_message_bytes` on the page allocator, unbounded by any cap, invisible to any counter. A sharded session (theme 01) that branches N children at once multiplies this.
2. **No quota on provider payload or tool result.** `buildRequestJson` (`openai_compatible.zig:204-237`) serializes the entire `messages` list into one `payload` slice with no upper bound; a context window that legitimately approaches the provider limit allocates a multi-megabyte buffer on the page allocator per turn. Tool results cap **captured** bytes at 64 KB but lose everything past it.
3. **No leak signal.** `page_allocator` has no `deinit` report. The 634 hand-written `defer allocator.free(...)` sites are the only defense; a single missed `defer` (easy — see the `nudge` at `loop.zig:250-251` which correctly defers, but a sibling that forgets would leak silently forever) accumulates across a multi-hour session with no diagnostic. AGENTS.md §XIV demands "oversized write payloads" as an adversarial test; today there is no allocator that would catch one.
4. **The TUI transcript is unbounded by construction.** `ChatState.messages` and `seen_progress_events` grow for the life of the process. A long streaming session (theme 10's "live assistant token stream") accumulates every delta byte forever; the only relief is process exit.

## What the competitor does

### Vercel Eve — V8 GC, in-memory arrays, no manual allocation

Eve is TypeScript on V8. It does not manage allocation at all — it manages **data structure growth** and relies on the GC to reclaim. Its compaction (`packages/eve/src/harness/compaction.ts`) is the clearest expression of the model:

- **Rebuilds the message array on every compaction.** `splitMessagesForCompaction` produces `{ older, recent }`, then `compact` returns `[...checkpointHead, ...capToolResults(input.older), ...input.recent]` (`compaction.ts:139-140`) — a fresh array spread-allocated from the old one. There is no arena; there is a new `ModelMessage[]` that the GC must later collect. Peak transient memory is `2 × messages` plus the summarizer call's own working set, exactly the doubling VANTARI's `rebuildProviderBaseMessages` inherits — except VANTARI pays it manually where Eve pays it in GC pressure.
- **Caps tool results by capping their serialized payload.** `capToolResults` (`compaction.ts:263+`) walks the older region and caps oversized tool-result payloads, because "serializing raw payloads into a prefix cap would keep" too much (`:259-261`). This is a **content cap applied at compaction time**, not a capture-time quota — the bytes already lived in the array before they were capped.
- **Token estimation drives the bound.** `estimateTokens` (`token-estimate.ts`, char-based heuristic) and `lastKnownInputTokens` are the only "size" the harness tracks; there is no byte counter, no allocation counter, no per-turn high-water mark. "Memory" in Eve means *tokens in the prompt*, not *bytes on the heap*.

**Limitation — and it is the VANTARI thesis:** Eve's failure mode is invisible until the GC pauses. A long session with large tool outputs grows the array, the summarizer allocates a parallel working set, and V8's generational GC eventually collects — but the operator has no signal, no per-turn bound, and no way to say "this turn is allowed 50 MB and no more." A GC pause mid-stream is felt as a stutter in `assistant_delta` rendering. VANTARI's manual allocator is the explicit version of what Eve leaves to the runtime.

### badlogic pi-mono — rolling buffer + spill-to-temp-file (the tool-result bound, done right)

pi-mono is TypeScript (not Rust — the `.refs/badlogic__pi-mono/packages/*/package.json` set confirms `coding-agent`, `ai`, `tui`, `agent` are all TS/Node). Its contribution to this theme is the **most disciplined tool-result bound in the harvest**, in `packages/coding-agent/src/core/bash-executor.ts`:

- **A rolling buffer with a hard byte ceiling.** `bash-executor.ts:58` sets `maxOutputBytes = DEFAULT_MAX_BYTES * 2`; the collector keeps `outputChunks` and `outputBytes`, and `while (outputBytes > maxOutputBytes && outputChunks.length > 1)` drops the oldest chunk (`:96-98`). The in-memory footprint is bounded *by construction*, not by truncation at the end.
- **Spill to a temp file when the buffer overflows.** `:69-70` creates `tempFilePath = join(tmpdir(), 'pi-bash-${id}.log')` and `tempFileStream = createWriteStream(tempFilePath)`; once `totalBytes > DEFAULT_MAX_BYTES` (`:85`) the full stream is tee'd to disk. The tool result carries `fullOutputPath?` (`:39`, surfaced in `messages.ts:36` and `tools/bash.ts:42`) so the model sees *"output truncated, full output at <path>"* (`messages.ts:94-95`) instead of silent data loss. `bash.ts:321-324` documents the same rolling buffer for the TUI's own tail truncation.
- **`truncated: boolean` is a first-class field.** The result envelope (`messages.ts:35`) carries `truncated` and `fullOutputPath` as typed fields — the bound is observable, not just enforced.

**What VANTARI steals:** the rolling buffer (bounded capture, not capture-then-truncate) and the `fullOutputPath` spill (no silent data loss). What VANTARI does *not* steal: pi-mono still runs on V8 with no turn arena and no leak detection; its bound is per-tool-result, not per-turn or per-payload.

### OpenAI Codex (Rust) — ownership + `Arc`/`Mutex`, no per-turn arena

The actual Rust reference in the harvest is `.refs/openai__codex/codex-rs/`. Its memory model is standard Rust ownership, not arenas:

- **`Arc<dyn Trait>` + `Mutex` for shared state.** `login/src/auth/storage.rs:234-235,315,325,327,329,330` and `auth/manager.rs:220,438,1283-1326` wrap auth stores and refreshers in `Arc<Mutex<...>>` — the shared-state pattern. There is no `bumpalo` or `typed_arena` dependency anywhere in the harvested crate set; the global allocator owns everything and lifetimes encode scope.
- **`String::with_capacity` for known sizes.** `login/src/server.rs:1045` does `let mut escaped = String::with_capacity(input.len())` — the one capacity hint in the harvest. Rust's ownership model makes the *lifetime* of every borrow provable, but it does not impose a *quota*; a `Vec` that grows without bound still grows without bound, the compiler just proves you free it eventually.

**What VANTARI steals:** the ownership clarity (`Arc`-equivalent: an explicit owner pointer per allocation region) and `with_capacity` hints. What VANTARI does *not* steal: Codex has no per-turn arena because its turns are RPCs handled by tokio tasks whose drop frees the task's allocations — a runtime-provided scope VANTARI does not have, because VANTARI's "task" is a `while (step < max_steps)` loop on one thread.

### Industry substrates

- **Zig `ArenaAllocator` for short-lived scopes.** The canonical Zig pattern (zig.guide, ziggit community) is one `ArenaAllocator` per request/turn, `arena.deinit()` at scope end frees everything at once — no per-allocation `defer free`. `DebugAllocator` (formerly `GeneralPurposeAllocator`) in debug/test builds reports unfreed allocations on `deinit()`, giving the leak signal `page_allocator` cannot. The standard recommendation: `DebugAllocator` in debug builds (leak detection), `ArenaAllocator` for per-turn/per-request scopes in release (speed). ([zig.guide/standard-library/allocators](https://zig.guide/standard-library/allocators/), [Ziggit: Allocators Best Practices](https://ziggit.dev/t/allocators-best-practices-anti-patterns/14043), [ITNext: Detecting Memory Leaks in Zig Using the GPA](https://itnext.io/detecting-memory-leaks-in-zig-using-the-general-purpose-allocator-b63be2cbd1f5)).
- **`bumpalo` / `typed-arena` (Rust) — per-request `Bump`, reset at end.** The established Rust pattern for request-scoped memory is `bumpalo::Bump::new()` at request start, `bump.reset()` at end; lifetimes encode the request scope, allocation is ~18× faster than the global allocator, and the whole region is freed in one op. `typed-arena` is the single-type variant. The concurrency caveat (`Bump` is `!Sync`; use `bumpalo-herd` or one `Bump` per task) maps directly onto VANTARI's detached-worker threads in `stdio_rpc.zig`. ([oneuptime.com: Optimize Memory with Arena Allocators in Rust](https://oneuptime.com/blog/post/2026-01-25-optimize-memory-arena-allocators-rust/view), [docs.rs/bumpalo](https://docs.rs/bumpalo), [manishearth: Arenas in Rust](http://manishearth.github.io/blog/2021/03/15/arenas-in-rust/)).
- **Region-based allocation in long-running processes.** The general systems-design principle — "each allocation belongs to a named region with a declared lifetime; regions are freed wholesale, not per-allocation" — is how jemalloc/MI per-thread arenas, Apache pool allocation, and nginx request pools all bound long-running memory. The agent-runtime literature frames the same idea as "transient per-turn state should be GC'd at turn boundaries; only durable memory is externalized" ([synergetics.ai: Solving Memory Leaks in AI Agents](https://synergetics.ai/blog/solving-memory-leaks-in-ai-agents), [Hugging Face Discuss: memory systems for long-running agents](https://discuss.huggingface.co/t/how-do-you-design-memory-systems-for-long-running-ai-agents/175584)).

## Why VANTARI does it better

1. **Named scopes beat a global allocator.** Eve runs on one V8 heap; pi-mono runs on one V8 heap plus per-tool temp files; Codex runs on one global allocator plus tokio task drops. VANTARI will declare **four typed scopes** — Turn, Provider payload, Tool result, UI frame — each a `std.mem.Allocator`-compatible region with an owner, a lifetime, and a bound (table below). Every allocation site in the backend is assigned to exactly one scope; an allocation that crosses its scope boundary is a bug the allocator catches, not a footnote in a code review. This is AGENTS.md §XVIII item 6 made literal.

2. **Per-turn `ArenaAllocator` makes compaction free and leak-proof.** Today `rebuildProviderBaseMessages` (`loop.zig:564-592`) clones every message, doubles transient memory, and relies on 634 hand-written `defer free` sites to reclaim. A turn arena (`std.heap.ArenaAllocator.init(child_allocator)` at `runPromptWithOptions` entry, `arena.deinit()` at exit) turns the whole turn into one allocation region: every `dupe`, `allocPrint`, `parseFromSlice`, and `append` inside the turn is freed by the single `arena.deinit()`. Compaction stops doubling — the rebuilt list lives in the same arena as the old one. The `cloneChatMessage` dance (`loop.zig:597`) becomes unnecessary because the arena owns the bytes. This is the Zig-canonical pattern, applied at the seam the executor already defines.

3. **`DebugAllocator` as the child gives the leak signal competitors lack.** Nesting `DebugAllocator` (a.k.a. `GeneralPurposeAllocator`) under the turn arena in debug builds produces a precise leak report on `deinit()` — unfreed bytes, allocation site, count. Eve and pi-mono have no equivalent: a leaked V8 reference is invisible until the GC decides to collect, and Codex's ownership model catches leaks at compile time only for provable scopes (a detached thread that drops a `RequestJob` without freeing it compiles fine). VANTARI gets compile-time ownership *and* runtime leak attribution: the §XIV adversarial list ("oversized write payloads", "duplicate context after provider overflow") becomes an allocator-level assertion instead of a hoped-for behavior.

4. **Quota-bounded tool results with spill, not silent truncation.** pi-mono's rolling buffer + `fullOutputPath` is the right shape; VANTARI's current `PipeCollector` already bounds capture at 64 KB but **loses** the overflow. VANTARI will add a quota on the tool-result allocator (a `FailingAllocator` wrapper that returns `error.OutOfQuota` past N bytes) **and** a spill path that tees overflow to `.var/sessions/<id>/tool-overflow/<call_id>.log`, returning `full_output_path` as a typed field in the tool-result envelope (theme 05's effect receipt). The model sees "output truncated, full at <path>" — pi-mono's invariant — without inheriting V8.

5. **Per-payload arena kills the three-defer dance.** `completeWithTransportAndHooks` (`openai_compatible.zig:184-202`) allocates `url`, `payload`, `response_body` on the page allocator with three separate `defer free`. A provider-payload arena (one `ArenaAllocator` per request/response cycle, deinit'd at function return) collapses the three into one `arena.deinit()` and bounds the payload: `buildRequestJson` writes into the arena, and if the serialized payload would exceed the context-window budget × an overhead factor, the arena's quota returns `error.PayloadOverQuota` *before* the network call — turning a late provider 413 into an early, typed compile error, which is theme 07's thesis applied to memory.

6. **Per-frame arena for the TUI kills the unbounded transcript.** `ChatState.messages` grows forever today. A UI-frame arena (`ArenaAllocator` per `buildTranscriptRows` call, already hand-emulated at `tui_chat.zig:1075`) absorbs all per-render `allocPrint`/`dupe` traffic; a separate bounded ring buffer (pi-mono's rolling-buffer pattern, ported to Zig) caps the retained `messages` list at N rows × M bytes with scrollback spilled to a session-local file. The terminal buffer size — the declared bound — becomes the actual cap, not a suggestion.

### THE FOUR SCOPES (target)

```text
┌─────────────────┬──────────────────────┬────────────────────────────────┬───────────────────────────────────┐
│ Scope           │ Owner                │ Lifetime                       │ Bound                             │
├─────────────────┼──────────────────────┼────────────────────────────────┼───────────────────────────────────┤
│ Turn            │ executor loop        │ one runPromptWithOptions call  │ max_tokens × overhead + step buf  │
│ (runPrompt)     │ (core/executor/loop) │ arena.deinit() at loop exit    │ (e.g. context_window × 1.5)       │
├─────────────────┼──────────────────────┼────────────────────────────────┼───────────────────────────────────┤
│ Provider        │ provider adapter     │ one request/response cycle     │ max context window bytes ×        │
│ payload         │ (providers/*)        │ arena.deinit() after parse     │ overhead (e.g. 128 KB headroom)   │
├─────────────────┼──────────────────────┼────────────────────────────────┼───────────────────────────────────┤
│ Tool result     │ tool runtime         │ one executeWithRunner dispatch │ output cap bytes (65536)          │
│                 │ (core/tools/runtime) │ freed on ChatMessage adoption  │ + spill to .var/.../overflow/     │
├─────────────────┼──────────────────────┼────────────────────────────────┼───────────────────────────────────┤
│ UI frame        │ TUI client           │ one render frame               │ terminal buffer size              │
│                 │ (clients/tui_chat)   │ arena.deinit() after render    │ (rows × cols × cell bytes)        │
└─────────────────┴──────────────────────┴────────────────────────────────┴───────────────────────────────────┘
```

Each scope is a `std.mem.Allocator`-typed value constructed from a typed `AllocatorScope` struct; the executor, provider adapter, tool runtime, and TUI each receive their scope's allocator instead of the raw `page_allocator`. The process-root `page_allocator` (or a single `DebugAllocator` in debug builds) remains the parent of all four, so leak detection at process exit still catches anything that escaped its scope.

## Pipeline items under this theme

### P1-15a: Allocation-scope audit and assignment
- **Contract:** every allocation site in `apps/backend/src/` is assigned to exactly one of the four scopes (Turn, Provider payload, Tool result, UI frame) or explicitly to the process root. An assignment map lives in `.docs/architecture/allocation-scopes.md`; a `build`-time or test-time lint flags any `page_allocator` use outside `main.zig` and the agent-service watch-job path. AGENTS.md §X ("allocation" as a named cost center) and §XVIII item 6 become auditable.
- **Mechanism:** introduce `pub const AllocatorScope = struct { name: []const u8, allocator: std.mem.Allocator, bound_bytes: usize, .. }` in a new `apps/backend/src/core/memory/scopes.zig` (kernel-owned, per AGENTS.md §IX). Construct one scope per turn in `runPromptWithOptions` (`loop.zig:93`), one per provider call in `completeWithTransportAndHooks` (`openai_compatible.zig:184`), one per tool dispatch in `executeWithRunner` (`runtime.zig:350`), one per frame in `buildTranscriptRows` (`tui_chat.zig:1075`). Each is backed by `std.heap.ArenaAllocator.init(child)` with `child = DebugAllocator` in `Debug`/`ReleaseSafe` and `child = page_allocator` in `ReleaseFast`. No new event type, no new storage — the scopes wrap allocators that already exist.
- **Test (AGENTS.md §XIV "oversized write payloads"):** a debug-build test runs a full turn (prompt → provider → tool → render) under the `DebugAllocator`-backed scopes and asserts `allocator.deinit()` reports zero unfreed bytes for each scope; an intentionally-leaked allocation (remove one `defer free`) fails the test with a precise attribution.
- **Proof:** the assignment map covers 100% of `apps/backend/src/` allocation sites; the debug-build leak report is empty after a representative session replay.

### P1-15b: Quota-bounded tool-result allocator with spill
- **Contract:** the tool-result scope enforces a declared byte quota per tool dispatch and, on overflow, spills the full output to `.var/sessions/<id>/tool-overflow/<tool_call_id>.<stream>.log`, returning a typed `full_output_path` field in the tool-result envelope alongside the existing `cap_reached` marker. No captured byte is silently lost; the model is told where the full output lives (pi-mono's invariant, ported). AGENTS.md §V ("bounded stdout/stderr deltas") and §XIV ("stdout/stderr cap markers", "oversized write payloads") are honored at the allocator layer.
- **Mechanism:** wrap the tool-result `ArenaAllocator` in a `QuotaAllocator` (`core/memory/quota.zig`) that tracks `allocated_bytes` against `bound_bytes` and returns `error.OutOfQuota` past the cap; in `PipeCollector.readLoop` (`runtime.zig:538`), on quota exhaustion, open a spill file under `.var/sessions/<id>/tool-overflow/` and tee subsequent frames to disk (the pi-mono `bash-executor.ts:69-90` pattern, in Zig). Extend `CommandOutput` (`module.zig:73`) with `full_stdout_path`/`full_stderr_path: ?[]const u8` and thread through `renderResult` (`builtin/shell_exec.zig:196`) and the `ToolFinished` event (theme 03 / `shared/protocol/events.zig:16`).
- **Test (AGENTS.md §XIV):** a `shell_exec` producing 1 MB of stdout, with `max_output_bytes: 16384`, returns the first 16 KB in-band, writes the remaining ~1008 KB to `tool-overflow/<call_id>.stdout.log`, and the tool-result envelope carries `{"cap_reached":true,"full_stdout_path":".var/.../tool-overflow/<call_id>.stdout.log","captured_bytes":16384}`. Re-reading the spill file yields the full 1 MB byte-identical.
- **Proof:** session/event evidence records the spill path; the §XIV adversarial list ("stdout/stderr cap markers", "oversized write payloads") asserts both the in-band cap and the on-disk full output.

### P1-15c: Per-turn arena for the executor loop
- **Contract:** `runPromptWithOptions` (`loop.zig:93`) constructs one turn-scoped `ArenaAllocator` at entry and `deinit()`s it at exit; every allocation inside the turn (the `messages` list, `ChatMessage` bytes, `allocPrint`'d logs, `parseFromSlice` results, `nudge`/`budget_message` strings) is served from it. `rebuildProviderBaseMessages` stops doubling transient memory because the rebuilt list lives in the same arena as the source. AGENTS.md §X ("allocation" cost center) gets a per-turn high-water counter.
- **Mechanism:** at `loop.zig:130`, replace `var messages = std.array_list.Managed(types.ChatMessage).init(allocator)` with `init(turn_arena.allocator())`; remove the per-message `defer message.deinit(allocator)` at `:131-134` (the arena owns them now); keep the session-record `defer session.deinit(allocator)` (session outlives the turn). Add a `turn_high_water_bytes` counter (a `CountingAllocator` wrapper, the HN-per-turn-count technique) to the existing `turn_terminal` payload (theme 03). `cloneChatMessage` (`loop.zig:597`) becomes an arena copy, not a page-allocator copy.
- **Test (AGENTS.md §XIV "duplicate context after provider overflow"):** a turn that triggers N compactions shows a flat high-water (clones live in the arena, not multiplied); a turn with a `DebugAllocator` child reports zero leaks on `deinit()`; the `turn_terminal` event carries `turn_high_water_bytes` that scales with `messages` content size, not with step count.
- **Proof:** session/event evidence shows `turn_high_water_bytes` per turn; a 100-step turn's peak memory is bounded by the arena's contents, not by `step × message_size`.

### P2-15d: Per-frame arena and bounded transcript ring for the TUI
- **Contract:** the TUI render path allocates all per-frame strings (status line, progress text, transcript rows, path tails) from a frame-scoped `ArenaAllocator` deinit'd after each render, and the retained `ChatState.messages` list is bounded by a rolling ring buffer (N rows × M bytes) with older scrollback spilled to a session-local file. The terminal buffer size — the declared bound — is the actual cap. AGENTS.md §X ("TUI frame" cost center) becomes a real budget.
- **Mechanism:** in `tui_chat.zig`, wrap the existing per-render `ArrayList(TranscriptRow)` (`:1075`) in a frame `ArenaAllocator`; route the ~40 `std.fmt.allocPrint` sites in `formatProgress`/`formatToolFinished`/etc. (`:1474-1631`) through it. Bound `ChatState.messages` with a ring (drop oldest when `messages.items.len > max_rows` or `total_bytes > max_bytes`), spilling dropped rows to `.var/sessions/<id>/tui-scrollback.jsonl` for later inspection. The `seen_progress_events` dedup set (`:360`) gets the same ring treatment.
- **Test (AGENTS.md §XIV "terminal scrollback under live streaming"):** a 10 000-event streaming session leaves `ChatState.messages` at ≤ `max_rows` entries and ≤ `max_bytes` total; the scrollback file contains the dropped rows in order; render-frame peak memory (frame arena high-water) is independent of session length.
- **Proof:** a long streaming session's resident TUI memory is flat, not growing; the scrollback file is replayable.

### P2-15e: Process-root `DebugAllocator` with leak attribution
- **Contract:** in `Debug` and `ReleaseSafe` builds, the process root allocator (the parent of all four scopes) is a `DebugAllocator` configured to print unfreed-allocation reports on process exit, attributing any allocation that escaped its scope to the scope name and call site. In `ReleaseFast`, the root remains `page_allocator` (no overhead). This is the leak signal competitors lack: Eve and pi-mono have V8 GC opacity; Codex has compile-time ownership but no runtime attribution for detached-thread escapes.
- **Mechanism:** in `main.zig`, replace the six `std.heap.page_allocator` references with a `const root = if (builtin.mode == .Debug or builtin.mode == .ReleaseSafe) ScopeDebugAllocator.init(std.heap.page_allocator) else std.heap.page_allocator;`; thread `root` (not the raw page allocator) into `cli.main`/`tui_chat.main`. The scope-debug wrapper tags each allocation with its owning scope name (`AllocatorScope.name`) so the exit report reads `leaked 4096 bytes in scope "turn" at loop.zig:250` instead of an opaque address.
- **Test (AGENTS.md §XIV):** a debug build that intentionally leaks (remove a `defer`) exits with a non-empty, scope-attributed report; a clean run exits silently; the report is gated off in `ReleaseFast` (no perf regression).
- **Proof:** the debug leak report is empty after a full representative session (CLI run, TUI session, stdio-RPC round-trip) in `Debug`; `ReleaseFast` shows no allocation-counting overhead.

## North-star link

A shard that branches into its own context window (theme 01) is only memory-safe if each shard's allocations die on convergence — otherwise N parallel children multiply the parent's live bytes by N, and a converged shard that forgot one `defer free` leaks forever against the parent's process. A typed event grammar (theme 03) that allocates per-event JSON on the page allocator is only safe if those bytes die at frame end. Tool effect receipts (theme 05) are only honest if the tool-result bytes are bounded and spillable, not silently truncated. The TUI workbench (theme 10) is only usable on a long stream if its transcript is bounded. Arena/quota discipline is what makes "the operator can observe the same causal chain the kernel will replay after cold start" (AGENTS.md §I) true at the byte level: deterministic scopes mean deterministic replay, and a per-turn high-water counter means the operator can see memory behavior as part of the causal chain, not as an opaque runtime secret. Without it, "no unbounded growth, no leak across turns, no OOM mid-session" (§XVIII item 6) is a wish; with it, it is a typed, tested, attributed invariant.

## Definition of done
- Four allocation scopes — Turn, Provider payload, Tool result, UI frame — are typed, owned, lifetime-bounded, and byte-bounded; every allocation site in `apps/backend/src/` is assigned to exactly one scope or to the process root (AGENTS.md §XVIII item 6).
- The executor loop runs each turn under a per-turn `ArenaAllocator`; compaction no longer doubles transient memory; a `turn_high_water_bytes` counter is emitted per turn.
- Tool results enforce a byte quota and spill overflow to `.var/sessions/<id>/tool-overflow/`, returning a typed `full_output_path`; no captured byte is silently lost (pi-mono's invariant, ported).
- The TUI render path uses a per-frame arena; `ChatState.messages` is bounded by a rolling ring with scrollback spill; resident TUI memory is flat across a long streaming session.
- In `Debug`/`ReleaseSafe`, the process root is a scope-attributed `DebugAllocator` that reports any escaped allocation on exit; `ReleaseFast` has no overhead.
- The §XIV adversarial list ("oversized write payloads", "stdout/stderr cap markers", "duplicate context after provider overflow", "terminal scrollback under live streaming") passes and gates promotion, with a native installed `vantari.exe` proof on Windows.
- No second allocator hierarchy, no parallel free-list (the existing `page_allocator.create(RequestJob)` hand-rolled scopes in `stdio_rpc.zig` and `agents/service.zig` are migrated onto the typed scopes), no leak that the debug report cannot attribute — the existing executor/provider/tool/TUI seams are reused, only the allocator they receive changes.
